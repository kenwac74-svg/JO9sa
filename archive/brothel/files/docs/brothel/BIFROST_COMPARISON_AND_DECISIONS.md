# JO9 창관모드 — 비프로스트 원형 비교 및 자동결정 v0.1

작성: 2026-10-08
기준: 비프로스트 마물창관 데이터/스크립트 직접 분석 + JO9 창관 v0.1 + 2026-10-08 확정사항.

## 1. 비프로스트 원형에서 직접 확인된 사실

- 튜토리얼은 고객의 '예산'을 고객이 가진 돈으로 정의한다.
- 고객은 '희망하는 창부' 항목으로 종업원의 특정 스탯을 중점 평가한다.
- 요구 스탯과 맞지 않아도 배정 자체가 금지되는 것이 아니라 만족도가 낮아지는 구조다.
- 고객 취향/성벽에 맞으면 낮은 육성 상태의 종업원도 일정 만족을 얻을 수 있다고 명시한다.
- 비프로스트 원본은 고객 '정력'을 별도 수치로 둔다. 만족도만큼 정력을 깎고 0까지 소진하면 보너스 후 고객이 소멸한다.
- 고객 데이터에는 money, hp, sp, tech, require 등이 별도 필드로 존재한다.
- 가게 랭크가 오르면 더 좋은 고객이 찾아오는 구조다. customerlist는 랭크 0~7마다 고객 후보 풀을 따로 가진다.
- '페로몬제'는 연장전 발생률 +50%를 명시한다. 고객 대사에도 연장/연장대금이 직접 존재한다.
- '출금 메달'은 특정 고객을 돌려보내고 다시 오지 못하게 하는 기능이 있다.
- '자라 엑기스'는 고객 정력 200 회복 기능이 있어 고객 지속력 관리가 별도 시스템임을 확인할 수 있다.

| 시설/성장 | 원본 별도 시스템 | JO9 v0.1 시설체계 | JO9 기획 우선 |

## 3. 자동 확정 — 추가 질문 없이 채택

### 3.1 고객 카드 풀
- 활성 고객 풀은 '한 번에 화면에 보이는 고객 수'와 '백엔드에 유지되는 지속 고객 카드 수'를 분리한다.
- 화면 대기열은 UI가 복잡해지지 않도록 소수만 노출하고, 지속 고객 풀은 창관 레벨에 따라 증가한다.
- 정확한 숫자는 UI 프로토타입에서 한 화면 수용량을 본 뒤 정한다. 이는 게임 규칙 충돌이 아니라 표시/밸런스 수치이므로 사용자 컨펌 없이 초안 제시 후 조정한다.

### 3.2 고객 생성
- 비프로스트처럼 완전 유니크 DB를 만들지 않고 템플릿+랜덤 조합.
- 생성 시 이름/초상/등급/핵심요구/추가선호/Trait/보유금을 하나의 persistent customer object로 묶는다.
- 카드가 소진/이탈/승급 재편으로 폐기될 때 새 객체 생성.
- 같은 초상/이름 재사용은 허용하되 동일 객체로 보지 않는다.

### 3.3 고객 돈 테이블
- 비프로스트의 실제 money 값은 고객별 프리셋이라 JO9의 하/중/상 3단계 테이블에 그대로 복사하지 않는다.
- JO9는 하/중/상 각각 '최소 기본금 + 추가금' 테이블을 만들고 구간이 겹치지 않게 한다.
- 수치는 JO9 경제 규모(기존 상점/임금/아이템 가격)를 분석한 뒤 자동 초안한다.

### 3.4 입장료
- 창관 레벨별 고정 입장료 테이블.
- 재방문 때마다 현재 레벨 입장료 적용.
- 잔액 <= 입장료이면 소진/이탈 처리.
- 승급으로 입장료가 올라 기존 고객이 조건을 못 맞추면 자동 소진 처리.

### 3.5 서비스료
- F=0%, S=100%를 양 끝점으로 두고 JO9 실제 등급 단계에 균등 간격으로 배분.
- S+는 경제적으로 S와 동일.
- 이 표는 JO9 등급 문자열/단계를 소스에서 확인한 뒤 자동 산출한다.

### 3.6 연장전
- 별도 화면 페이즈를 만들지 않는다.
- 같은 고객/같은 접객원으로 연속 처리하며 종업원 행동력만 추가 소모.
- A 이상만 후보.
- 발생률은 핵심요구 충족수, 추가선호 충족수, 단계형 초과충족 %를 입력으로 사용.
- 비프로스트의 페로몬제 같은 '연장전 확률 보정' 개념은 향후 시설/아이템 효과로 재사용 가능.

### 3.7 지명
- 신규 지명: A 이상 + 실제 연장전 완료 후 방문 종료 시 33%.
- 기존 지명자 배정 시 숨은 보정 적용.
- 다른 접객원을 써도 기존 지명 자동철회 없음. 새 지명 성공 시 교체.
- 기존 지명자를 이용해 B 이하이면 철회.
- 지명 보정은 연장전 확률에도 반영.

### 3.8 고객 등급 풀
- Lv1~3 하100%.
- Lv4~6 하25%/중75%.
- Lv7~10 중25%/상75%.
- Lv4/Lv7 진입 시 지속 고객 풀을 즉시 재편.
- 지명 고객도 보호하지 않는다.

## 4. 기존 문서와 충돌하여 폐기할 항목

- 고객 HP/정력/정신을 모두 별도 임시 스탯으로 둔다는 초기안: 폐기. 현재안은 고객 지속력을 돈으로 통합.
- '고객 정력 0=착정완료' 문구: JO9에서는 '잔액 <= 현재 입장료'로 대체.
- '종업원 스태미나 0에서 추가 행동력 0.5' 복원 문구: 현재 확정된 일반 1:1 페이즈당 종업원 행동력 1 규칙과 충돌하므로 폐기/원문 재검증.
- 비프로스트 고객 money 값을 JO9 기본금 테이블로 그대로 쓰는 안: 폐기.

## 5. 실제로 남은 핵심 결정사항

아래는 수백 개 질문으로 쪼갤 대상이 아니다. 구현 전에 한 번에 묶어서 결정한다.

1. **그룹 접객**: 1.5명 규칙의 정확한 의미와 돈/종업원 행동력/만족도 보정식.
2. **연장전 확률식**: 이미 입력변수는 확정됐으므로 계수만 정하면 됨.
3. **고객 Trait 시스템**: 부자(가칭) 포함. 종류/상충/중복/경제효과.
4. **창관 레벨별 활성 고객 풀 크기와 입장료/고객 기본금 숫자표**: JO9 경제 분석 후 초안 제시.
5. **시설 효과의 현재 확정안 재검증**: v0.1의 스위트룸/샤워실/휴게실/보건소/자동경영/마담/홍보실/조교실/훈련도구/네크로관을 현재 고객·돈 구조에 맞춰 충돌검사.

그 외 세부 수치는 기획자가 먼저 초안을 만들고 사용자는 충돌/취향이 큰 부분만 승인한다.

# 6. 그룹 접객 설계 — 자동 결정안 v1

## 원형 확인
비프로스트 원본에는 실제로 '그룹 중견급 이사' 같은 그룹 고객 카드가 존재한다. 다만 제공된 데이터에서 그룹 고객만을 위한 별도 접객 알고리즘/배율표는 명확히 확인되지 않았다. 따라서 '그룹=1.5명'은 비프로스트에서 그대로 복사할 수치가 아니라 JO9 기획에서 확정해야 하는 보정값으로 본다.

## JO9 그룹 고객 정의
- 그룹 고객은 UI/저장상 고객 카드 1장이다. 개별 구성원을 별도 객체로 생성하지 않는다.
- 이름/초상/등급/핵심요구/추가선호/Trait/잔여 보유금/지명 상태도 카드 하나에 귀속.
- 일반 고객과 동일한 매칭·지명·연장전 엔진을 사용한다. 별도 미니게임을 만들지 않는다.
- 그룹 여부만 group 플래그와 보정계수로 처리한다.

## 1.5명 규칙 — 제안 확정안
'1.5명'은 고객 수가 아니라 접객 부하 계수로 정의한다.

### 종업원 행동력
- 일반 1:1 접객: 행동력 1 소모.
- 그룹 접객: 행동력 1.5 소모.
- JO9 행동력이 정수 저장이라 0.5를 직접 저장하기 어렵다면 내부 half-point(2=1행동력) 또는 그룹 접객 2회 누적 시 추가 1 차감 방식으로 구현한다.
- 그룹 연장전도 동일하게 추가 1.5 소모.

### 고객 보유금
- 그룹이라는 이유만으로 서비스료 계산률을 1.5배하지 않는다.
- 대신 그룹 고객 생성 시 최초 보유금 테이블에 1.5배 계수를 적용한다.
- 이유: 현재 JO9에서는 고객 돈 자체가 고객 지속력이다. 서비스료율까지 1.5배하면 지속력 증가와 회당 소진 증가가 동시에 적용되어 그룹의 체감 지속시간이 일반 고객과 비슷해지는 상쇄가 생긴다.
- 따라서 그룹은 돈이 많아 오래 남지만, 한 번의 만족도 판정 공식은 일반 고객과 동일하다.

### 입장료
- 카드 1장이므로 입장료는 1회분만 낸다.
- 그룹 인원수 배수 입장료는 적용하지 않는다. 그룹의 경제적 가치 증가는 보유금 1.5배에 포함한다.

### 만족도/요구
- 핵심요구 1~3, 추가선호 0~3, 단계형 ±20/최대 ±40, 추가선호 +20 규칙은 일반 고객과 동일.
- 그룹 전용으로 요구 슬롯을 늘리지 않는다.
- 그룹이라는 이유로 만족도에 자동 페널티를 주지 않는다. 부담은 종업원 행동력 1.5 소모로 표현한다.

### 연장전/지명
- A 이상이면 일반 고객과 동일한 연장전 확률식을 사용.
- 연장전 발생 시 동일 종업원 고정.
- 그룹 연장전의 종업원 행동력 소모도 1.5.
- 신규 지명/지명 유지 규칙도 일반 고객과 동일.

### 카드 소진
- 일반 고객과 동일하게 서비스 후 잔여금이 현재 입장료 이하이면 소진/이탈.
- 그룹이라고 별도의 착정완료 조건을 만들지 않는다.

## 이 설계의 이유
1. 기존 확정인 '그룹=약 1.5명 처리'를 종업원 부하에 명확하게 반영.
2. 고객 돈=행동력이라는 최신 결정과 충돌하지 않음.
3. 일반 고객 엔진을 그대로 재사용하므로 QSP 구현 복잡도가 낮음.
4. 그룹의 보상이 더 크지만 종업원도 더 빨리 지쳐 경영 선택이 생김.
5. 그룹 전용 만족도/요구/연장전 코드를 만들 필요가 없음.

## 구현 시 검증할 것
- JO9 행동력 변수가 0.5를 안전하게 표현 가능한지 확인.
- 불가능하면 내부적으로 행동력 단위를 2배 스케일링하거나 group fatigue counter를 둔다.
- 그룹 최초 보유금 1.5배 적용 후 하/중/상 금액구간 비중첩 원칙이 깨지는지 확인. 깨지면 그룹 고객은 별도 그룹 보유금 테이블로 분리한다.

## 사용자 재확인이 필요한 경우
- 그룹 고객의 '1.5명'이 과거 원문에서 행동력 부하가 아니라 다른 의미였다는 근거가 발견될 때만 재질문한다.

# 7. 연장전 확률식 — 자동 결정안 v1

## 비프로스트 원형에서 확인된 근거
- 원본 아이템 데이터의 Pheromone Booster는 "clients extending their time (+50%)"로 명시되어 있어 연장전이 **확률 사건**임을 확인할 수 있다.
- 제공 데이터에서는 연장전의 기본 확률 공식 자체는 노출된 텍스트 데이터에서 확인되지 않았다.
- 따라서 JO9의 확률식은 원본의 '확률 사건 + 외부 보정 가능' 구조만 차용하고, 계산식은 현재 JO9 요구/선호 시스템에 맞춰 설계한다.

## 확정 전제
- 1차 최종 만족도가 A 미만이면 연장전 확률 = 0%.
- A 이상일 때만 연장전 판정.
- 입력값은 이미 확정된 다음 3개:
  1. 핵심요구 충족 개수
  2. 추가선호 충족 개수
  3. 단계형 핵심요구의 초과충족(+20/+40)
- 지명 보정으로 얻은 충족/+40도 실제 충족과 동일하게 계산.
- 연장전은 동일 종업원 고정, 별도 UI 페이즈 없음.

## 제안 공식

### 1) 기본 확률
A 이상 진입 시 기본 20%.

### 2) 핵심요구 충족 보너스
핵심요구 1개 완전 충족당 +10%.

- 하급(핵심 1): 최대 +10
- 중급(핵심 2): 최대 +20
- 상급(핵심 3): 최대 +30

핵심요구가 단계형일 경우 '요구 기준 충족'까지가 이 +10의 대상이고, 초과분은 아래 오버 보너스로 따로 계산한다.

### 3) 추가선호 보너스
추가선호 충족 1개당 +10%, 최대 +30%.

추가선호는 원래 만족도에서 +20%씩 강한 보너스를 주지만, 연장전에서는 절반 계수(+10)를 사용한다. 이유는 선호 3개만으로 연장전이 과도하게 확정되는 것을 막기 위함.

### 4) 단계형 초과충족 보너스
핵심요구의 양(+) 방향 초과충족 총합을 절반 계수로 확률에 반영.

- +20% 초과충족 -> 연장전 +10%
- +40% 초과충족 -> 연장전 +20%
- 단계형 요구가 여러 개면 합산.
- 음(-) 방향 미달은 별도 확률 페널티로 다시 빼지 않는다. 이미 최종 만족도 A 이상 조건을 통과하기 어렵게 만들기 때문에 이중 페널티를 피한다.

### 최종식
연장전확률(%) =
20
+ (핵심요구 충족수 × 10)
+ (추가선호 충족수 × 10)
+ (양의 단계초과충족% ÷ 2)

단, A 이상일 때만 계산.

## 예시

### 간신히 A
핵심 1개 충족, 선호 0, 오버 0:
20 + 10 = 30%

### 좋은 중급 매칭
핵심 2개 충족, 선호 1, 단계 오버 +20:
20 + 20 + 10 + 10 = 60%

### 상급 완벽 매칭
핵심 3개 충족, 선호 3, 단계 오버 합계 +40:
20 + 30 + 30 + 20 = 100%

### 극단적 초과매칭
단계형 요구가 여러 개라 오버 합계가 +80 이상이면 100%를 넘을 수 있으므로 **연장전 확률 자체만 100%에서 캡**한다.
이는 매칭 보정 총합에 상한이 없다는 기존 결정과 충돌하지 않는다. '효과값'에는 상한이 없지만 확률은 100%를 넘을 수 없기 때문이다.

## 만족도 등급 A/A+에 별도 가중치를 두지 않는 이유
연장전 확률은 이미 '요구 충족수 + 선호 충족수 + 오버%'라는 원인값을 직접 사용한다. A와 A+ 자체에 추가 보너스를 또 주면 같은 성과를 이중 계산한다. 따라서 A 이상은 게이트 역할만 한다.

## 향후 시설/아이템 보정
비프로스트의 Pheromone Booster처럼 연장전 확률에 직접 가산하는 효과를 허용한다.
- 예: 페로몬 계열 효과 +X%p.
- 적용 순서: 기본 공식 계산 -> 시설/아이템/이벤트 가산 -> 0~100% clamp.
- 실제 +50%p 아이템을 JO9에 그대로 넣는 것은 아직 결정하지 않는다.

## 판정
이 공식은 현재 확정사항과 충돌이 없고, 낮은 A는 연장전이 '가능하지만 확정 아님', 완벽한 상급 매칭은 사실상 연장전을 보장하는 구조다. 사용자가 원한 '요구 만족 개수와 만족 오버%가 연장전 발생확률과 연동'을 직접 구현한다.

# 8. 고객 Trait 시스템 — 비프로스트 비교 기반 자동 설계 v1

## 비프로스트 원형에서 직접 확인
비프로스트 CUSTOMER 데이터의 state에는 다음 특성이 실제 존재한다.
- 부호
- 동정
- 오덕
- 성병
- 아저씨
- 난동
- 테크니션
- 가로채기
- 오크

한 고객에게 state가 여러 개 중첩된 데이터도 존재한다. 예를 들어 Ex-Hero는 '부호 + 오덕', 일부 고객은 '난동 + 테크니션 + 가로채기 + 오크'까지 가진다.
또한 HUGOU 데이터가 별도 존재하며 같은 고객 원형의 money가 크게 증가한 변형들이 확인된다. 따라서 비프로스트는 고객의 등급/요구와 별개로 행동·경제·위험 특성을 중첩하는 구조를 실제 사용한다고 판단한다.

## JO9 채택 원칙
- 고객 Trait은 고객 등급(하/중/상), 핵심요구, 추가선호와 **별도 레이어**다.
- Trait은 0개 이상 가질 수 있다.
- 같은 고객 카드가 재방문하면 Trait도 그대로 유지한다.
- 고객 카드가 폐기되면 Trait도 함께 사라진다.
- Trait은 요구 슬롯을 차지하지 않는다.
- 핵심요구/추가선호의 상충 검사와 Trait 상충 검사는 별도 테이블로 관리한다.
- 비프로스트의 Trait 명칭/효과를 그대로 복사하지 않고, JO9에서 의미가 있는 것만 치환한다.

## v1 Trait 카테고리

### A. 경제 Trait
#### 부자 (가칭)
이미 확정된 Trait.
- 같은 등급의 일반 고객보다 최초 보유금 증가.
- 높은 만족도에서 팁 보너스 증가.
- 핵심요구 개수에는 영향 없음.
- 하/중/상 모든 등급에 붙을 수 있음.
- 정식 명칭은 추후 결정.

#### 짠돌이 (가칭)
자동 설계.
- 최초 보유금은 등급 최소구간을 유지하되 랜덤 추가금 상단이 낮다.
- 팁 없음.
- 별도 만족도 페널티는 없음.
- 부자와 상충.

이 Trait은 고객 경제 다양성을 만들지만 핵심 매칭 엔진을 건드리지 않는다.

### B. 위험/운영 Trait
#### 문제손님 (가칭)
비프로스트 '난동'의 JO9 치환 후보.
- F 이하 실패가 발생했을 때 공통 실패 이벤트의 비용/후유증을 강화하는 보정자.
- 평상시 만족도에는 직접 페널티 없음.
- 실패 이벤트 자체는 기존 확정대로 1종을 유지하고, 결과 수치만 Trait으로 가중하여 이벤트 트리를 늘리지 않는다.

#### 감염위험 (가칭)
비프로스트 '성병'의 JO9 치환 후보.
- JO9에 실제 질병/위생 판정이 연결 가능한 경우에만 활성화.
- 서비스 후 기존 JO9 질병/위생 시스템에 확률 보정.
- 새 질병 시스템을 별도로 만들지는 않는다.
- 기존 게임에서 안전하게 연결할 훅이 없으면 v1 구현에서 제외한다.

### C. 취향/행동 Trait
#### 능숙한 손님 (가칭)
비프로스트 '테크니션'에서 아이디어 차용.
- 고객 요구나 추가선호를 늘리지 않는다.
- 서비스 결과의 대사/이벤트 변형 또는 종업원 상태 변화에만 관여하도록 제한.
- 구체 효과는 JO9 기존 성행위/상태 로직 확인 후 결정.

#### 집착형 (가칭)
비프로스트 '가로채기'를 그대로 복사하지 않고 JO9 지명 시스템에 맞게 치환할 수 있는 후보.
- 지명 발생/유지와 연동 가능한 Trait 후보.
- 다만 현재 지명 시스템 자체가 이미 충분히 복잡하므로 v1 기본 구현에서는 비활성 후보로 둔다.

### D. 정체성/플레이버 Trait
비프로스트의 '아저씨/오크/오덕/동정'처럼 고객 캐릭터성을 주는 Trait.
- JO9에서는 초상/이름/대사 세트와 연결.
- 경제/만족도에 무조건 효과를 주지 않는다.
- 일부는 추가선호 생성 가중치에만 영향을 줄 수 있다.
- 시스템 Trait과 플레이버 Trait을 분리해 밸런스 폭증을 막는다.

## Trait 생성 규칙 — 자동 결정

### 개수
- 일반 고객: 0~2개.
- 0개가 가장 흔함.
- 상급 고객일수록 1~2개 등장 확률을 조금 높인다.
- 특수 이벤트 고객만 예외적으로 3개 이상 허용.
- 비프로스트처럼 무제한 중첩은 하지 않는다. JO9의 핵심요구+추가선호+지명까지 이미 판정요소가 많기 때문.

### 중복/상충
- 동일 Trait 중복 금지.
- 부자 ↔ 짠돌이처럼 논리적 반대 Trait은 동시 생성 금지.
- Trait 상충표를 별도 데이터로 둔다.
- Trait과 핵심요구/추가선호가 의미상 모순되는 경우도 생성 단계에서 배제할 수 있도록 cross-conflict 테이블을 둔다.

### 등급과의 관계
- Trait은 4번째 고객 등급이 아니다.
- 하/중/상 어느 등급에도 붙을 수 있다.
- 단, Trait별 최소 고객등급을 설정할 수 있다. 위험도가 큰 Trait은 중/상급부터 등장시키는 방식.
- 기본 고객등급의 핵심요구 개수(1/2/3)는 Trait 때문에 변하지 않는다.

## 팁 시스템 — 부자 Trait을 위해 최소 설계

팁은 서비스 이용료와 분리된 추가 수익이다.
- F~B: 팁 없음.
- A 이상: 부자 Trait 보유 시 팁 판정.
- 연장전 완료 시 팁 판정 보너스.
- 팁은 고객 잔여 보유금에서 추가 차감한다. 고객이 가진 돈 이상을 생성하지 않는다.
- 팁으로 잔여금이 현재 입장료 이하가 되면 정상적으로 고객 카드 소진.
- 정확한 팁 %는 경제 테이블 설계 단계에서 서비스료와 함께 산출한다.

## v1 실제 구현 우선순위
1. 부자(가칭) — 구현
2. 짠돌이(가칭) — 구현
3. 문제손님(가칭) — 구현 가능하나 실패 이벤트 비용 구조 확정 후 연결
4. 감염위험 — JO9 기존 질병 훅 확인 후 결정
5. 능숙한 손님/집착형 — 후순위
6. 플레이버 Trait — 대사/초상 데이터 제작 단계에서 확장

## 비프로스트에서 그대로 가져오지 않는 것
- '오크/아저씨/오덕' 같은 원본 세계관 명칭을 시스템 효과로 그대로 복제하지 않는다.
- '가로채기'의 원본 행동을 확인하지 않은 상태에서 임의 효과를 만들지 않는다.
- HUGOU의 원본 money 숫자를 JO9 경제에 그대로 사용하지 않는다.
- Trait 때문에 핵심요구 슬롯 수를 늘리지 않는다.

## 현재 사용자 확인이 필요한 충돌
없음. 부자 Trait의 '예산 증가 + 높은 만족도 팁 증가'는 기존 확정과 일치한다. 나머지는 JO9 구현을 단순하게 유지하기 위한 v1 후보이며, 실제 소스 훅이 없는 Trait은 자동으로 후순위 처리한다.

입장료는 원본 홍등가 3~100 스파크 서비스와 충돌하지 않는 낮은 범위로 둔다.

### 그룹 고객
일반 동급 보유금의 1.5배 기본 제안은 확정된 '등급별 돈 구간 비중첩'과 충돌 가능:
하급 그룹 최대 298.5 < 중급 최소 300 으로 안전하나,
중급 그룹 최대 748.5 > 상급 최소 700 이므로 겹침.
따라서 '그룹은 무조건 1.5배'를 그대로 적용하면 금액구간 비중첩 원칙 위반.
**충돌 해결 제안**: 그룹을 별도 부하 1.5로 유지하고, 그룹 초기보유금은 해당 고객 등급 구간의 상한에서 캡. 중급 그룹 450~499 구간 등. 단 이 경우 그룹의 경제적 이득이 약해지므로 사용자 확인을 요구하지 않고 경제 시뮬레이션 단계에서 조정할 잠정안으로 표기.

## 중요 설계 충돌 — 해결 필요

1. 고객 보유금 = 고객 지속력, 서비스료는 '입장료 후 잔액의 %'다. 서비스료율이 일정하면 수익이 기하급수적 감소하므로 고액 고객을 지나치게 오래 유지할 가능성이 있다. 활성 고객 풀의 자동 재편/소진 조건으로 이를 제어할 것.
2. S-/S+ 중 S를 100% 지급이라고 표현한 결정과 코드의 단계명이 다르다. v1은 S- 와 S+ 모두 100%, S+의 차이는 멘트만이라고 해석하는 잠정안.
3. 서비스료를 100%로 받으면 잔액 0이 되므로 자동 착정완료. 반대로 낮은 만족도로도 잔액 <= 다음 입장료가 되면 소진. 이는 현재 합의와 일치.
4. 기존 입장료/보유금 재방문 로직은 게임 원본에 없으므로 추가 구현 필요.
