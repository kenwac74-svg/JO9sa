# JO9 창관모드 — 네크로관 기능 명세 v0.1

- 상태: **설계 기준안**
- 작성 기준: 사용자 제안안 검토·정리
- 적용 브랜치: `brothel`
- 범위: 저장 구조, 구형 세이브 변환, 상태 전이, 영업 페이즈 연결, UI 요구사항
- 구현 상태: 미구현

## 0. 검토 결론

이 기준안은 기존 네크로관 초안보다 구현 가능성이 높고 저장 안정성도 좋다. 특히 다음 결정은 그대로 채택한다.

- 사망일 포함 30일의 고정 사용 가능 기간
- 창관 Lv.4 / Lv.7 / Lv.10에서 네크로관 Lv.1 / 2 / 3 해금
- 시설 레벨별 독립 슬롯 1 / 2 / 3명
- 건설비 150%, 유지비 125%, 정수 스파크 단위 올림
- 사망자에게 체력·정신력·행동력을 새로 만들지 않음
- 슬롯 하나당 영업 페이즈 기본 1회 사용
- 일반 창관 정산 엔진 재사용
- 사망 기록은 자동 삭제하지 않고 계속 보존
- 구형 세이브에는 변환 시점부터 30일 전부 보장

이 문서는 과거의 다음 제안을 대체한다.

- 접객 횟수에 따라 시신 보존수명을 추가 차감하는 방식
- 네크로관을 창관 Lv.10에서 한 번에 해금하는 방식
- 네크로관 종업원에게 별도 행동력·체력·정신력을 부여하는 방식

초기 기획에서 확정된 다음 원칙은 유지한다.

- 네크로관은 일반 창관의 **사망자 전용 특수 확장 슬롯**이다.
- 살아 있는 종업원 정원과 분리한다.
- 시설 Lv.1 / 2 / 3에서 슬롯 1 / 2 / 3명을 제공한다.
- 네크로관 내부에는 처형 기능을 넣지 않는다.
- 사망 기록을 별도로 보존하고 일반 창관의 매칭·정산 구조를 재사용한다.

## 1. 기능 기준표

| 항목 | 기준안 |
|---|---|
| 사용 가능 기간 | 사망일 포함 30일 |
| 기간 계산 | `available_until = death_day + 29` |
| 유효 판정 | `current_day <= available_until`이면 이용 가능 |
| 기간 만료 | 기록 보존, 배치 불가, 배치 중이면 자동 해제 |
| 구형 세이브 | 최초 변환일을 임시 사망일로 지정하고 30일 전부 보장 |
| 시설 해금 | 창관 Lv.4 / Lv.7 / Lv.10에서 네크로관 Lv.1 / 2 / 3 |
| 슬롯 | 시설 레벨별 1 / 2 / 3명 |
| 건설비 | 같은 레벨 시설 기준비의 150%, 올림 |
| 유지비 | 같은 레벨 시설 기준비의 125%, 올림 |
| 운영 제한 | 슬롯 하나당 영업 페이즈에서 기본 1회 사용 |
| 체력·정신력·행동력 | 사용하지 않음 |
| 기록 삭제 | 자동 삭제하지 않음 |

### 1.1 비용 산식

특정 일반 시설 하나를 비교 대상으로 삼지 않고, 시설 시스템의 공통 레벨별 기준비를 사용한다.

```text
necro_build_cost[level]
= ceil(facility_build_cost_baseline[level] * 1.50)

necro_maintenance_cost[level]
= ceil(facility_maintenance_cost_baseline[level] * 1.25)
```

공통 기준비 테이블이 확정되기 전에는 실제 스파크 금액을 넣지 않는다.

### 1.2 조정 가능한 임시 수치

다음 네 항목만 플레이테스트에 따라 조정할 수 있는 임시 수치로 본다.

1. 사용 가능 기간 30일
2. Lv.4 / Lv.7 / Lv.10 해금
3. 건설비 150% / 유지비 125%
4. 슬롯당 영업 페이즈 1회

그 밖의 저장·상태·변환 규칙은 세이브 안정성을 위한 구조적 기준이다.

## 2. 사망 기록 데이터 모델

### 2.1 식별자

같은 캐릭터가 부활 후 다시 사망할 수 있으므로 `character_id` 단독으로 기록을 식별하지 않는다.

```text
record_id = character_id + ":" + death_sequence
```

`character_id + death_sequence`를 복합키로 사용하거나 위 형식의 `record_id`를 별도 저장한다.

### 2.2 권장 구조

```text
death_record
├─ record_id
├─ character_id
├─ death_sequence
├─ name
├─ portrait_path
├─ death_day
├─ death_cause
├─ owner_id
├─ body_state
├─ record_state
├─ available_until
├─ assigned_slot_index
├─ eligibility_reason
├─ migration_source
├─ snapshot
└─ data_version
```

### 2.3 필드 정의

| 필드 | 의미 |
|---|---|
| `record_id` | 사망 회차까지 포함한 고유 기록 ID |
| `character_id` | 원래 캐릭터 ID |
| `death_sequence` | 같은 캐릭터의 누적 사망 회차 |
| `name` | 사망 당시 이름 스냅숏 |
| `portrait_path` | 사망 당시 초상화 경로 |
| `death_day` | 게임 내 사망일 |
| `death_cause` | 사망 원인 코드 |
| `owner_id` | 사망 당시 소유자 |
| `body_state` | `PRESENT` 또는 `LOST` |
| `record_state` | 이용·배치·종료 상태 |
| `available_until` | 마지막 이용 가능 게임 날짜 |
| `assigned_slot_index` | 미배치 시 `-1`, 배치 시 슬롯 번호 |
| `eligibility_reason` | 현재 배치 가능 또는 불가 사유 코드 |
| `migration_source` | `native`, `legacy` 등 생성 출처 |
| `snapshot` | 네크로관 판정에 필요한 사망 당시 캐릭터 데이터 |
| `data_version` | 사망 기록 스키마 버전 |

기존 제안의 `disposition_state`는 의미가 모호하므로 `record_state`로 이름을 고정한다. `eligibility_state`는 상태와 사유를 한 값에 섞지 않고 `record_state + eligibility_reason`으로 분리한다.

### 2.4 스냅숏 범위

`snapshot`에는 네크로관의 매칭·정산에 실제 필요한 값만 복사한다.

- 외모 등급
- 외형·체형
- Trait
- 성적 능력
- 사망 당시 상태조건
- 종합 등급
- 네크로관 이미지·이벤트 선택에 필요한 태그

다음 값은 사망 이후 변화하지 않으며 회복·훈련도 하지 않는다.

- 행동력
- 체력·정신력
- 기분·복종·응석
- 위생·영양
- 일일 명령 상태

원본 캐릭터 객체가 삭제되더라도 스냅숏만으로 UI와 매칭 판정이 동작해야 한다.

### 2.5 대체 표시값

- 이름이 비어 있거나 읽을 수 없으면 `이름 없는 사망자`
- 초상화 경로가 없거나 파일을 찾지 못하면 네크로관 기본 초상화
- 알 수 없는 사망 원인은 `UNKNOWN`

기록 화면은 외부 이미지 파일이 사라져도 열려야 한다.

## 3. 구형 세이브 변환

### 3.1 일회성 변환

사망일이 없는 구형 기록은 세이브 최초 변환 시 한 번만 다음 값으로 보정한다.

```text
death_day = migration_day
available_until = death_day + 29
death_cause = UNKNOWN
migration_source = legacy
data_version = CURRENT_DEATH_RECORD_VERSION
```

배치 가능 조건:

- 현재 플레이어 소유 기록
- 육체 소실 기록 없음
- 부활 상태 아님

### 3.2 반복 변환 방지

세이브 또는 사망 기록 컬렉션에 다음 값을 저장한다.

```text
death_record_migration_version = CURRENT_DEATH_RECORD_VERSION
```

로드 때 버전이 이미 같거나 높으면 `death_day`와 `available_until`을 다시 계산하지 않는다.

### 3.3 변환 실패 원칙

구형 기록에서 필수값이 부족한 경우 캐릭터를 삭제하거나 임의로 복원하지 않는다.

- 기록은 사망 기록부에 남긴다.
- `record_state = LOST` 또는 적절한 불가 상태로 둔다.
- `eligibility_reason`에 원인을 기록한다.
- 플레이어 캐릭터 목록을 임의 변경하지 않는다.

## 4. 상태 모델

### 4.1 사망 기록 상태

```text
AVAILABLE → ASSIGNED → EXPIRED
     │          │
     ├──────────┼→ SOLD
     ├──────────┼→ LOST
     └──────────┴→ REVIVED
```

| 상태 | 의미 |
|---|---|
| `AVAILABLE` | 기간과 소유권이 유효하며 배치 가능 |
| `ASSIGNED` | 네크로관 슬롯에 배치 중 |
| `EXPIRED` | 사용 기간 만료 |
| `SOLD` | 판매 또는 소유권 이전 |
| `LOST` | 도축·소각·육체 소실 |
| `REVIVED` | 부활하여 생존 상태로 복귀 |

### 4.2 시설 상태와 기록 상태 분리

유지비 미납은 사망 기록의 상태가 아니다.

```text
facility_state = ACTIVE | SUSPENDED
```

- 유지비 미납 시 `facility_state = SUSPENDED`
- `ASSIGNED` 상태와 슬롯 번호는 보존
- 접객만 금지
- 재가동 때 모든 배치 대상의 유효성을 다시 검사

### 4.3 시설 레벨 하락

슬롯이 줄어들면 뒤쪽 슬롯부터 해제한다.

- 해제된 기록이 여전히 유효하면 `AVAILABLE`
- 기간 만료·소유권 변경·육체 소실이면 해당 종료 상태
- 별도의 `WAITING` 상태는 만들지 않는다.

### 4.4 부활과 생존 명부 정원

부활 시 사망 기록은 `REVIVED`가 되고 네크로관에서 즉시 제거된다.

생존 명부 정원이 부족하면 부활한 캐릭터는 **생존자 대기열**로 이동한다. 이는 사망 기록 상태와 분리된 시스템이며, 사망 기록을 다시 `AVAILABLE`로 돌리지 않는다.

### 4.5 재사망

같은 인물이 다시 사망하면:

```text
death_sequence += 1
new record_id 생성
새 death_day 및 available_until 계산
새 snapshot 저장
```

이전 사망 기록은 기록부에 그대로 남긴다.

## 5. 유효성 검사

다음 시점에 동일한 공통 검사 함수를 호출한다.

1. 영업 페이즈 시작
2. 네크로관 화면 진입
3. 슬롯 배치 직전
4. 고객에게 배정하기 직전
5. 유지비 납부 후 시설 재가동
6. 세이브 로드 직후

### 5.1 권장 검사 순서

```text
record exists
→ not REVIVED
→ current owner valid
→ body PRESENT
→ current_day <= available_until
→ not assigned to another slot
→ facility ACTIVE when service begins
```

### 5.2 배치 불가 사유 코드

```text
NONE
EXPIRED
NO_OWNERSHIP
BODY_LOST
REVIVED
ALREADY_ASSIGNED
FACILITY_LOCKED
FACILITY_SUSPENDED
INVALID_RECORD
```

UI 문구는 코드와 분리해 관리한다.

## 6. 영업 페이즈 연결

### 6.1 공통 정산 엔진 재사용

새 정산 엔진을 만들지 않는다.

```text
venue_type = NORMAL | NECRO
```

공통 처리:

- 고객 생성·방문
- 핵심요구·추가선호 매칭
- 만족도 등급 계산
- 입장료·서비스료·팁 정산
- 연장전·지명
- 고객 카드 유지·소진
- 창관 성장 반영

네크로관 전용 처리:

- 사망 기록 유효성 검사
- 네크로관 슬롯 선택
- 페이즈 사용 횟수 검사
- 네크로관 이벤트·이미지 선택

### 6.2 슬롯 사용 제한

각 영업 페이즈 시작 시 슬롯별 카운터를 초기화한다.

```text
phase_use_count[slot] = 0
```

배정이 확정되어 서비스 정산이 시작될 때:

```text
if phase_use_count[slot] >= 1:
    사용 불가
else:
    phase_use_count[slot] += 1
```

연장전은 기존 확정대로 **같은 접객 체인의 연속 처리**이므로 `phase_use_count`를 추가 증가시키지 않는다.

그룹 고객도 고객 카드 하나의 접객이므로 사용 횟수는 1회다.

### 6.3 저장 위치

`phase_use_count`는 사망 기록의 영구 데이터가 아니라 영업 페이즈 런타임 상태다.

- 페이즈 중간 저장을 지원하면 영업 세션 데이터에 저장
- 다음 영업 페이즈 시작 시 반드시 초기화
- 사망 기록 스냅숏에는 넣지 않음

### 6.4 정산 중복 방지

화면 재진입이나 이벤트 자료 누락으로 정산이 반복되지 않도록 접객마다 고유한 처리 ID를 만든다.

```text
resolution_id = phase_id + customer_card_id + record_id
```

이미 완료된 `resolution_id`는 다시 정산하지 않는다.

이벤트 이미지나 대사가 없어도:

1. 판정 결과는 유지
2. 기본 결과창 표시
3. 정산은 정확히 한 번 실행
4. 영업 종료 판정 갱신

### 6.5 이미지와 대사

이미지·대사는 `event_id`로만 조회한다. 경로를 정산 코드에 직접 하드코딩하지 않는다.

```text
event_id = necro.<result_family>.<grade_or_condition>
```

해당 이벤트 자료가 없으면 중립 기본 결과창으로 폴백한다.

## 7. 비용·정지·재가동

### 7.1 유지비 납부

영업 정산 주기의 기존 시설 유지비 처리에 네크로관을 포함한다.

- 유지비 미납: `SUSPENDED`
- 배치 상태 보존
- 신규 배치·접객 금지
- 날짜 경과와 30일 만료는 계속 진행

유지비 미납이 사용 가능 기간을 멈추지는 않는다.

### 7.2 재가동

유지비 납부 후:

1. 시설 상태를 `ACTIVE`로 변경
2. 배치 슬롯 순서대로 기록 유효성 검사
3. 무효 대상 자동 해제
4. 유효 대상만 기존 슬롯 복구

## 8. UI 요구사항

경로:

```text
특별관 → 네크로관
```

### 8.1 시설 정보

- 네크로관 레벨
- 다음 단계 해금 창관 레벨
- 건설비·강화비
- 유지비와 납부 상태
- 사용 중 슬롯 / 전체 슬롯
- 시설 상태 `ACTIVE` 또는 `SUSPENDED`

### 8.2 사망 기록 목록

- 이름
- 초상화 또는 기본 대체 초상화
- 사망일·사망 원인
- 남은 사용 가능 일수
- 현재 상태
- 배치 불가 사유

남은 일수 표시:

```text
remaining_days = max(0, available_until - current_day + 1)
```

### 8.3 조작

- 배치
- 배치 해제
- 시설 건설·강화
- 유지비 납부 또는 시설 재가동
- 사망 기록부 진입

### 8.4 표시 원칙

- 기능 정보만 표시
- 체력·정신력·행동력 바를 만들지 않음
- 만료 기록도 사망 기록부에서 계속 조회 가능
- 상태 코드는 사용자용 문구로 변환

---

## 9. 사망 기록부

네크로관 이용 가능 여부와 관계없이 모든 사망 기록을 보존한다.

필터 예시:

- 전체
- 이용 가능
- 배치 중
- 기간 만료
- 판매·소유권 이전
- 육체 소실
- 부활

기록부는 자동 삭제 기능을 제공하지 않는다. 향후 수동 보관함·페이지 분할은 UI 편의 기능으로 추가할 수 있지만 데이터 삭제와 동일시하지 않는다.

---

## 10. 오류 처리와 안전 규칙

- 원본 캐릭터가 삭제되어도 `snapshot`으로 화면과 판정 유지
- 잘못된 슬롯 번호는 자동 해제 후 기록 보존
- 중복 배치는 먼저 발견한 유효 슬롯만 유지하고 나머지 해제
- 날짜 역행 또는 손상된 날짜는 기록을 삭제하지 않고 `INVALID_RECORD` 처리
- 구형 세이브 변환은 버전당 한 번만 실행
- 유지비 미납 중에도 만료일은 정상 진행
- 부활·판매·육체 소실은 정산 직전에 다시 검사
- 정산과 이벤트 출력은 분리하고 정산은 한 번만 실행

---

## 11. 구현 전 검증 항목

1. JO9에서 사망 직전 캐릭터 데이터를 복사할 수 있는 공통 경로
2. 자연사·전투·처형 등 모든 사망 분기의 공통 훅 가능 여부
3. 판매·도축·소유권 변경·부활의 실제 변수와 이벤트 위치
4. 게임 날짜와 세이브 버전 변수
5. 시설 공통 건설비·유지비 기준 테이블
6. 영업 페이즈 시작·종료 및 중간 저장 지원 여부
7. 사망 기록용 신규 배열·문자열 배열의 QSP 세이브 복구
8. 기존 고객 정산 함수에 `venue_type` 분기를 넣을 수 있는지

실제 변수명과 location은 원본 QSP 확인 전 임의로 고정하지 않는다.

## 12. 테스트 기준

### 데이터·변환

- 같은 캐릭터가 두 번 사망해도 기록 ID가 충돌하지 않음
- 구형 세이브 로드 후 30일이 한 번만 부여됨
- 재로드해도 임시 사망일이 갱신되지 않음
- 초상화 파일이 없어도 기록 화면이 열림

### 날짜·상태

- 사망 당일 포함 정확히 30일 이용 가능
- 31번째 날 자동 만료
- 만료 시 배치 중이면 자동 해제
- 판매·육체 소실·부활 시 즉시 해제
- 시설 중단 중에도 기간 만료 진행

### 슬롯·페이즈

- Lv.1 / 2 / 3에서 슬롯 1 / 2 / 3개
- 한 영업 페이즈에서 슬롯별 1회만 사용
- 연장전은 추가 사용 횟수로 계산하지 않음
- 다음 영업 페이즈에서 사용 횟수 초기화
- 시설 레벨 하락 시 뒤쪽 슬롯부터 해제

### 정산·이벤트

- 일반 창관 정산과 동일한 고객 결과를 사용
- 이벤트 이미지·대사가 없어도 정산은 정확히 1회
- 화면을 다시 열어도 돈·만족도·고객 상태가 중복 변경되지 않음
- F 이하와 정상 성공, 연장전, 지명 경로 모두 정상 종료
