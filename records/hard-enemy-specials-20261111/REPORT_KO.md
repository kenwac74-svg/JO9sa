## 실제 동작

인게임 설정 `difficulty_setting=2`에서 기존 일반 공격 1~3개와 해당 적의 아직 사용하지 않은 특수기를 하나의 목록에 넣고 균등 선택한다. 일반 공격 수는 원래 클래스 한도(졸개1·일반2·정예3)를 유지한다. 기존 24종의 30개 특수기가 대상이다. 타입·피해 타입·본문·짧은 설명이 비었거나 기본 특수 피해가 정의되지 않은 항목은 제외한다. 효과 코드가 비어 있는 기존 순수 피해 특수기는 포함한다. 재추첨 반복문을 추가하지 않았다.

사용 이력은 `jo9_enemy_special_used[(적 인덱스-1)*3+특수기 슬롯]`의 0/1 배열이다. 같은 종류 적 둘도 서로 독립적으로 같은 기술을 한 번씩 쓸 수 있다. 새 전투의 기존 `jo9_fog['resuming']=0` 초기화 안에서만 지우며, 교대·메뉴 재작성·전투 화면 재표시는 유지한다. 일반 QSP 배열로 저장되므로 별도 저장 포맷·마이그레이션은 없다. 이전 저장에 배열이 없으면 기본값0으로 읽는다.

`исчадие`, `чудовщиное_исчадие`, `исчадие_арены`의 두 번째 특수기 효과는 하드 실행 시에만 기존 효과 문자열의 `[1]`을 `[i]`로 바꿔 시전자에게 적용한다. 기존 강화99·해제용1과 피해 계산 전 효과 실행 순서를 유지한다. 기존 `ии_безумный_архимаг` 미존재 AI 주소만 하드에서 표준 AI로 연결했다.

쉬움·보통의 원래 일반 공격 선택문과 공격 정의는 유지했다. 30개 기술의 수치·지속시간·본문·짧은 설명·효과 정의를 수정하지 않았다. 기존 일반 공격 상태 키의 `<br>` 불일치, 캐릭터 생성 `game_difficulty`, 기존 난이도 보너스, 춘향·물약은 이번 QSP 변경 대상이 아니다.

## 코드 위치와 사용 설명

`code-references.json`은 최종 QSP의 디코딩된 로케이션 본문 기준 1-based 줄을 기록한다.

호출자는 표준 AI이며, 적별 플래그는 같은 AI가 효과 실행 뒤 기록한다. 피해 계산·전투 로그 출력은 기존 경로가 소비한다. `#противники` 정의·`рассчет_вреда`·`jo9_fog` 초기화 규약에 의존한다. helper만 삭제하면 남은 호출이 깨지므로 기능 제거 시 해당 표식의 호출·기록·초기화도 함께 되돌려야 한다. 이후 수동 수정이 있으면 과거 QSP 전체 덮어쓰기 대신 이 패치 차이를 역적용해야 한다.

## 저장 복원 검사의 범위

설치 FastQSP가 실제 쓴 SAV를 코덱으로 읽어 배열 `[0,1,0,0,1,0,1]`과 왕복 바이트 보존을 확인했다. 별도 QSP5.7 공식 `QSPOpenSavedGame` API로 그 파일을 복원하고, 복사본 저장·재복원 뒤 배열 전체가 같은 것도 후보·설치본 모두 통과했다. 해당 보고서는 `save-api-candidate.json`, `save-api-installed.json`이다.

설치 FastQSP의 진단 `OPENGAME` 명령은 SAV를 게임 파일처럼 처리해 실패했다. 기존 `records/varbase-repair-20261021/MANUAL_KO.md`에 기록된 제한과 같다. 실패는 통과에 합산하지 않았으며 제품 코드 우회는 추가하지 않았다. 보조 구형 DLL은 helper의 local 선언을 오류114로 거부하므로 helper 실행 증거로 쓰지 않는다. 그 실행은 설치 FastQSP에서만 검증했다. 보조 API는 DEBUG=1 CRC 우회와 비운 진단 onload를 사용한다. 실제 FastQSP 저장 선택 UI, 엄격 CRC, 개인 기존 저장의 전체 로드 경로와 육안 화면은 미검증이다. 기존 개인 저장은 읽거나 쓰지 않았다.

일반 게임 EXE의 추가 수동 확인 항목은 하드 전투에서 특수기 표시, 동일 적의 동일 기술 재사용 여부, 교대·저장 후 불러오기에서 사용 이력 유지다. 화면과 GUI 저장 불러오기 확인은 사용자에게 남아 있다.

## 복구·재현·정리

유일 복구 기준본은 이 폴더의 `before.qsp.gz`이며 메타데이터는 `runtime-source-before.json.gz`다. 두 압축 모두 복원 바이트를 검증했다. 적용기가 만든 중복 WORK 백업은 이 압축 기준본과 같은 해시임을 확인한 뒤 이번 생성분만 지웠다. 다른 기존 백업은 건드리지 않았다.

`task.cjs`의 snapshot은 최초 작업 전용이다. 재현은 `red`(예상 exit1) → `prepare` → `replay` → `native` → `save-fixture candidate` → `run candidate` → `save-api-prepare candidate` 순서이며 마지막 API는 `C:/Windows/SysWOW64/WindowsPowerShell/v1.0/powershell.exe -NoProfile -ExecutionPolicy Bypass -File run-save-api.ps1 -Config G:/Codex/tmp/hard-enemy-specials-20261111/save-api-candidate/config.json`로 실행한다. RED/prepare는 압축된 기준본을 사용한다. `install`은 현재 WORK가 적용 전 해시일 때만 쓰도록 차단되어 있으며 재검사에 필요하지 않다. `native <현재QSP> installed`와 설치 단계의 save-fixture/run/API 호출로 설치본만 다시 검사할 수 있다. 이미 있는 진단 폴더를 재사용하지 않는다.
