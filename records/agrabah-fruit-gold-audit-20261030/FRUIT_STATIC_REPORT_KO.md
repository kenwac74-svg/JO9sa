# 아그라바 과일 구매 정적 검사 — 2026-10-30

현재 WORK 및 보호 원본 JO9O를 메모리에서 읽은 조사다. 게임·세이브·원본 파일은 변경하지 않았다. 실제 실행 검증은 부모 에이전트가 별도로 수행한다.

## 확인한 결론

현재 과일 구매와 환전은 모두 숫자 변수 `gold`를 사용한다. 별도 금화 지갑·배열·단위가 섞인 정적 불일치는 찾지 못했다. 다만 과일 구매 메뉴에는 **잔액 외에 아그라바 퀘스트 11단계와 미구매 조건**이 있다. 따라서 돈이 충분해도 메뉴가 비활성일 수 있다. 이 조건은 JO9O 원본부터 동일하다.

### 작은 과일 바구니

- 메뉴: `#options:7088~7089`. `active[$event['Akabur_quest']]=11`, `fruits_minibox=0`, 그리고 `gold>=25 또는 sparks>=250`일 때 활성화.
- 실행: `interaction_city:26882~26898`, ID `30212`. `gold<25`이면 스파크250, 그렇지 않으면 금화25를 차감하고 `Fruits_minibox=1`로 설정.
- 원본: `#options:6637~6638`의 조건과 실행 ID가 현재와 글자 그대로 동일.

### 연회용 과일

- 메뉴: `#options:7090~7091`. 같은 퀘스트11단계, `fruits_maxibox=0`, 그리고 `gold>=1000 또는 sparks>=10000`일 때 활성화.
- 실행: `interaction_city:26899~26916`, ID `30213`. `gold<1000`이면 스파크10000, 그렇지 않으면 금화1000을 차감하고 `Fruits_maxibox=1`로 설정.
- 원본: `#options:6639~6640`의 조건과 실행 ID가 현재와 동일.
- 원본부터 회색 메뉴 조건에 다른 퀘스트 단계 전체를 포괄하는 항이 없어, 퀘스트11단계가 아니고 미구매일 때 이 항목이 회색 대신 아예 없는 조합도 가능하다. 이는 금화가 사라지는 근거가 아니라 기존 메뉴 조건 범위다.

## 환율과 구매 가능 금액

현재 환전은 스파크100/250/500/1000 → 금화10/25/50/100이며, 역환전은 금화1당 스파크10이다. 따라서 스파크1000을 환전해 얻은 금화100으로는 금화1000짜리 연회용 과일을 살 수 없다. 이미 구매한 항목은 1회 구입 플래그 때문에 다시 사지 못한다.

`$event['Akabur_quest']`의 실제 진행도 키는 `#event_base:7`의 러시아어 HTML 문자열이다. JO9O 원본 `#event_base:5`의 값과 같아 현재/원본의 이 키 차이는 확인되지 않았다.

## 실제 엔진 검사에 필요한 최소 상태

기본 위치는 `$place='balsam_boutique'`, `sp_txt=3`; `#options`의 해당 과일 메뉴를 평가한다. 메뉴 배열과 도구 기본값은 실제 저장 상태+refresh_database로 준비한 뒤 다음 조합을 비교한다.

1. `active[$event['Akabur_quest']]=11`, `fruits_minibox=0`, `gold=25`, `sparks=0`: 작은 바구니 활성, ID30212 후 gold0·minibox1.
2. 같은 상태, `gold=24`, `sparks=249`: 작은 바구니 비활성.
3. 같은 상태, `gold=0`, `sparks=250`: 작은 바구니 활성, 스파크 대납으로 sparks0·minibox1.
4. `stage=11`, `fruits_maxibox=0`, `gold=1000`, `sparks=0`: 연회 과일 활성, ID30213 후 gold0·maxibox1.
5. `stage=11`, `fruits_maxibox=0`, `gold=100`, `sparks=0`: 연회 과일 비활성.
6. `stage=10 또는 12`, `gold=2000`, `sparks=20000`: 충분한 자금과 무관하게 퀘스트 조건으로 구매 불가.
7. `stage=11`, 해당 구매 플래그1: 충분한 잔액이 있어도 재구매 불가.

환전 결과 저장·로드 뒤 이 상태값이 그대로 유지되는지 검증해야 특정 세이브 제보를 좁힐 수 있다. 제보자의 실제 세이브는 없으므로 여기서 사용자의 실패 원인을 퀘스트 단계 또는 금액 착오로 단정하지 않는다.
