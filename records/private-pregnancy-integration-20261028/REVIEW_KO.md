# 개인실 임신 원문 상태 연결 진단 독립 검토

2026-10-28. `native-unmodified.cjs`와 새 probe/ten 계획·결과·합성 SAV 및 실제 생성 QSP를 읽기 전용으로 대조했다. 이 검토자는 게임·엔진을 실행하지 않았고 제품·기존 세이브·다른 보고서를 수정하지 않았다. 이 파일만 작성했다.

## 정적 경계

검토 스크립트 SHA256은 `f045ca07db20e832486121f640aeaa0056a25802655b6bad82559f34cb37d49f`다. 입력은 f652 백업이고, 당시 현행 e830과의 본문 차이는 안개 AP의 `jo9_fog_relay` 한 곳뿐이다. 이번 임신 경로에 그 변경을 섞지 않는다.

실제 ten 진단 QSP(`ce05878f6db4584333c7051c61b835b8901a7bfd91215ee2fc6752244ffa561e`)를 f652와 직접 비교했다. 변경된 인코딩 필드는 Start 본문과 `interaction_screen` 본문 두 개뿐이며 다른 모든 인코딩 필드는 완전히 같다. 나머지 273개 로케이션의 본문도 같다. `interaction`, `interaction_result`, `snk_room_bridge`, `#static_base`, `#dynamic`, `$slave_traits`, `$newloc`, `jo9_traits` 및 임신 계산 본문은 바꾸지 않았다. 일일 함수는 원문의 정의·호출을 추출해 Start에서 사용하며 전체 하루 이벤트를 실행하는 방식은 아니다.

원문 `interaction_result:1919`의 최종 목적지는 `interaction_screen`이다. 진단은 이를 QA 복귀로 교체한다. 원문 장면 renderer 출력은 실행하지 않지만, 원래 renderer 첫 부분의 `$special_action[txt]` 같은 화면 단계 동작까지 검증한 것으로 넓혀 말하면 안 된다. 이 검사의 범위는 renderer 도착 전 상호작용 결과와 이어서 실행한 특성/repair·일일 상태 연결이다.

기존 정규식 필터는 새 진단에서 사용하지 않는다. 원문 수락 판정과 결과 분기는 그대로 실행되며 fixture가 `res/diligence/sex_acceptance` 결과를 직접 대입하거나 성공 분기를 강제로 호출하지 않는다. 성인 age2·일반 type1435·정상 생식값0·현재 표식0·일반 능력 범위에서 시작한다. 다만 수락하기 좋은 합성 능력값과 배란 전날을 정한 사례이며 모든 일반 상태·거절·자연 20~30일 플레이의 대표 표본은 아니다. 실제 사용자 SAV나 저장된 동적 함수 캐시는 로드하지 않는다.

## 최종 증거 대조

- 단일 probe의 wrapper 기록은 `TIMEOUT/pass=false` 그대로다. 별도 보존된 최종 SAV에는 사례1/index1/inflight0/renderer1/assertions28/stage40이 있다. 따라서 **상태 계산 완료와 출력 파이프 기반 종료 검출 실패를 구분**해야 하며 probe를 단순한 native PASS로 다시 집계하면 안 된다.
- 이후 ten 결과는 `STATE_COMPLETE/pass=true`다. 최종 SAV의 완전 파싱·재직렬화가 일치하고, 사례10/index10/inflight0/renderer10/assertions284/stage40을 직접 확인했다. 284는 사례별28조건×10 + bridge 진입4조건이다. 10사례는 주 노예·조수 직접 경로2, 개인실 직접 경로4, 개인실 bridge 경로4다.
- 종료 판정은 새 폴더의 최종 SAV가 존재하고 위 종료 수치가 전부 맞을 때만 `STATE_COMPLETE`로 바뀐다. 과거 SAV를 재사용하지 않도록 실행 폴더가 이미 있으면 중단한다. ten의 완료 이벤트는 `COMPLETE_SAV_VERIFIED` 한 건이며, 첫 probe 이후에 실행된 기록과 일치한다. CLI 자체가 이전 probe PASS를 강제하는 것은 아니므로 이 순서는 실행 기록에 근거한다.
- 관찰은 합계 임신3/비임신7이다. 임신3은 개인실 bridge 3사례이고, 나머지 직접·bridge 사례는 비임신이다. 각 결과를 새 확률 추정이나 직접 경로의 임신 불가 근거로 사용하면 안 된다. 실제 상호작용 후 표식3~5, 특성/repair 후 표식 보존, 일일 순회·대상 연결 등 모든 조건은 해당 사례에서 완료했다.
- 결과의 보호 파일5개는 전후 해시가 같고 `userSaveLoaded/userSaveWritten`은 모두 false다. 보호 원본·현재 WORK·기존27번 세이브에 수리를 적용한 실행이 아니다.

## 보고 제약과 결론

stdout/stderr는 ten에서 모두0바이트다. 이는 Qt 파이프에서 출력을 관측하지 못했다는 뜻이며 원문 MSG 발생0의 증거가 아니다. 새 wrapper는 원문 MSG를 저장·전달하지 않지만 엔진의 MSG 실행 자체를 막지는 않는다. 따라서 **‘원문 장면 renderer를 우회하고 원문 MSG 문장을 보고서/로그에 내보내지 않았다’와 ‘MSG가 전혀 발생하지 않았다’를 구분**해야 한다. 후자는 이번 증거로 확인할 수 없다.

이 경계 안에서 새 접근에 추가로 고쳐야 할 상태 계산 코드 결함은 발견하지 못했다. 이전 세 QA timeout·필터의 loop/중괄호 손상은 진단 결함이며 제품 회귀 근거가 아니다. 새 10사례의 상태 연결 완료는 이전 미완료를 보완하지만, 사용자의 실제 개인실 임신 제보를 재현하거나 수리한 것이 아니다. 실제 SAV·저장 캐시·전체 GUI 및 하루 동선은 계속 미검증으로 남긴다는 결론이 타당하다.
