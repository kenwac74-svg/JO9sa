# 최신 이미지 조회 보정의 부작용 점검

검사 대상은 WORK `jack.qsp` SHA256 `5aeff11fffe6e5f2523749987577f42dab870f4d0adee0df385375f9eefb074f`이다. 게임 본체·JSON·이미지·세이브·Full·배포물은 이 검사에서 수정하지 않았다.

`jo9_seed_role_images`에서 `INDIE_EVENT_FULLIMAGE_20261023` 블록을 제거하면 직전 백업의 같은 location 본문과 바이트 단위로 같다. 기존 도나 충돌 정리와 조회 부분의 변화는 없다. 새 블록은 이미 선언된 local 임시 변수와 함수 반환값만 쓰며 인물 배열이나 전역 등록 배열을 쓰지 않는다.

조회 호출부는 `display_pic` 10줄, `display_fullimage` 1줄, `end_day_screen` 18줄, `interaction` 6줄, `interaction_city` 4줄, `interaction_screen_city` 1줄, `stasis_cell` 1줄, `sex_interaction_result` 1줄이다. 마지막 줄의 조건식에는 조회 함수가 두 번 적혀 있다. 인물 해제 전에 배경을 저장하는 기존 호출 순서도 그대로다. 외부 location에서 이름을 나눠 만든 것으로 의심되는 `jo9_seed` 참조는 발견하지 못했다.

## 실제 엔진 검사

게임 엔진 `game/engine/jack.exe`의 SHA256은 `f75032d79ecb58eeb7b969cd3f774d66b091fca38a360acdabd782e03a46c6e6`이다. 전체 게임 복제 대신 작은 진단 QSP를 만들었고, 제품의 조회·display_pic·display_fullimage 본문은 그대로 넣어 해시를 대조했다. 현재 JSON에서 이미지 등록값만 가져왔으며 기대 결과는 별도의 데이터로 미리 기록했다.

수정한 진단 도구의 12개 경로가 모두 PASS다. 미리 만든 조회 사례 55,685개와 정리 이후 반복 조회 7,882개, 합계 63,567회가 통과했다. 1,126개 전체 인물의 기본/역할/빈/개별 지정/이미 선택된 경로, 명시적 역할 요청, 역할 팩만 빈 경우, 모든 팩이 빈 경우, 팩 변수 자체가 없는 경우, 도나 구 별칭 96개와 네 가지 제외 임신 별칭, 알 수 없는 ID, 전역 정리와 JSON 등록 순서를 검사했다. 합성한 동일 ID 별칭 충돌에서는 기본 이미지가 우선하는 현재 코드의 순서를 확인했다.

별도로 실제 호출문 124회, display_pic 40회, display_fullimage 52회, 성관계 결과 조건식의 두 인물 경로를 실행했다. `special_action`에 저장하는 배경 코드는 생성 후 dynamic으로 실행해 경로를 확인했다. 네 대표 ID는 새 이사벨라2571, 구 이사벨라2323, 도나96, 에게야2579이다. ID·상태와 13개 인물 배열을 비교했고, 일반 조회 시험에서는 74종 이미지 등록 배열도 전후 스냅샷과 비교했다. 기존 정리 자체를 시험하는 경우에는 의도한 전역 별칭 제거 96개를 확인하고 인물 배열 보존을 비교했다.

직전 백업의 조회 본문을 넣은 대조 시험은 `JO9_QA_ASSERT_FAILED_CASE_0_ID_2571` 메시지로 의도대로 실패했다. 시간 초과를 재현 성공으로 계산하지 않았다.

## 동작의 경계

- 여러 인물이 같은 구 경로를 공유해도 입력 ID의 등록을 사용한다. 2571과2323은 각각 자신의 팩을 반환한다.
- 등록과 다른 사용자 지정 경로와 빈 경로는 보존된다. 사용자가 지정한 경로가 그 ID의 등록 별칭과 완전히 같으면 기존 기본값과 구분할 수 없으므로 같은 교체 규칙을 따른다.
- 같은 ID의 현재 기본/역할 별칭이 겹치는 사례는 없다. 앞으로 겹치는 데이터를 만들면 `fullimage`, `fullmade`, `fullsecretary`, `fullmistress` 순서로 먼저 맞는 값이 선택된다.
- 일반 fullimage 요청에서 역할 팩이 없으면 해당 ID의 title 팩으로 대체한다. 명시적 fullmade/fullsecretary/fullmistress 요청은 이 새 분기에서 바꾸지 않는다. 따라서 팩 구성이 일부 빠진 설치에서는 두 요청 방식의 경로가 다를 수 있으며, 이는 현재 구현의 명시된 차이다.
- 등록 자체가 없으면 원래 경로와 기존 도나 처리를 유지한다. 함수가 JSON 등록을 새로 읽거나 세이브를 이관하지는 않는다. 오래된 저장 상태에 최신 indpack 등록이 있는지는 별도의 실제 로드 검증 대상이다.
- 이 검사에서 이미지 보정에 의한 새로운 전역/인물 상태 변경이나 선택 파일 누락은 발견하지 못했다.

## 검증 한계와 진단 도구 수정

등록 데이터는 실제 JSON에서 생성했으므로 커스텀 엔진의 JSON 역직렬화 자체를 새로 증명하는 시험은 아니다. 임의의 미래 ID·파일명·사용자 경로 전체를 유한한 시험으로 증명하지는 않는다. 이벤트 전체의 선행 조건·수치 효과·플레이 순서, 실제 화면 픽셀, 저장 선택 UI는 이 이미지 시험의 범위 밖이다. 정지실의 실제 출력문에는 `interior_change`의 HTML 외형 처리만 항등 시험 대역을 썼고, 경로 조회 본문은 바꾸지 않았다.

처음 만든 진단 코드의 FOR 줄에 콜론이 빠져 시간 초과가 발생했다. 진단 코드만 바로잡고 정적 `checkSyntax` 검사를 생성기에 추가했다. 이후 최소 로딩·단일 조회·30사례 제어 시험, 명시적 실패 대조, 최종 12개 시험을 통과했다. 초기 시간 초과나 잘못된 실행 파일 경로 시험은 제품 결함이나 통과 결과로 세지 않았다. QSP 헤더 세 필드도 실제 WORK의 값을 그대로 복사하도록 했다.

주요 증거는 `image-native-results.json`, `image-native-marker-logs.json`, `image-static-summary.json`, `image-caller-inventory.json`, `image-input-manifest.json`, `image-red-client-results.json`, `image-red-baseline-detection-control-stderr.log`에 보관했다. 재생성 스크립트는 `check-all-images.cjs`이며 엔진을 자동 실행하지 않는다.
