# UI 좌표 소유권·반복 패턴 검토

2026-10-27 WORK QSP `1f43f75a…`, base.css `a782d60e…`와 `inline-and-engine-geometry.json`을 대조했다. 운영 파일은 변경하지 않았다. 좌표 감사는 표시 규칙 조사이며 모든 정적 후보가 실제 버그라는 뜻은 아니다.

## 원칙: 한 화면 안에서 원점을 한 곳만 소유

배경은 뷰포트 원점인데 상위 패널은 `MAINDESC → 장면 root → 내부 left/top`을 모두 더하면 위치가 밀린다. 전체 화면은 전용 고정 캔버스가 원점을 소유하거나, 엔진 본문 영역이 원점을 소유하도록 둘 중 하나를 선언한다. 내부 그림과 버튼은 그 소유자의 자식 좌표만 사용한다. 서로 다른 화면 종류의 숫자를 하나로 바꾸는 작업은 별개다.

| --- | --- | --- |

전투의 이전 실제 엔진 측정은 전장 `(243,1)`로, 설계 `(242,0)`에 본문 `(1,1)`이 더해진 상태였다. 작은 오차는 확인됐지만 모든 전투에서 큰 밀림이 발생한다는 결론은 아니다. 기존 전투 helper에는 `MSG_X=350`만 있고 `MAINDESC_X/Y` 선언이 없어 이전 장면 원점 상속을 우선 점검할 가치가 있다.

## 전역 교체가 위험한 구체 사례

- 공용 `#bg`는 정적으로 확인되는 로케이션만 33곳에서 사용된다. `interaction_screen_city`, `shop_general`, `guild`, `barn`, 개인실, 경매 등과 `display_fullimage` 같은 동적 helper도 포함한다. 여기의 `(4,3)`을 0으로 바꾸는 것은 전체화면 하나의 수리가 아니다.
- 엔진은 `div`를 table처럼 취급한다. 게임오버에서 795×595 컨테이너가 1280×800 그림의 크기로 확장됐고, 전투 시험에서는 빈 패널 높이와 기술 목록이 달라졌다. 새 component 내부의 선택적 `display:block`은 필요하지만 모든 `div`에 적용하면 기존 정렬·자동 높이·툴팁을 바꾼다.
- 전역 `position:relative` 추가도 안전한 정리가 아니다. 기존 절대 좌표 자식의 containing block을 바꾸어 같은 숫자의 의미 자체가 달라진다.
- `#jo9_tv_panel`과 닫기 링크는 body 포털이며 높은 z-index를 가진다. 새로운 조상에 transform이나 독립 stacking context를 만들면 숫자가 커도 다른 레이어 뒤로 들어갈 수 있다.

## 실제 확인된 CSS 적용 범위 문제

`runtime-stylesheet-scope.json`의 최소 비프로필 장면은 명시 CSS link가 0개이고 프로필 DOM도 없는데, 실제 엔진 CSSOM에 `#jo9_tv_panel` 규칙이 존재했다. 같은 stylesheet에서 base의 `body::before(top45,height755)` 뒤에 jo9_traits_view.css의 `body::before(top0,height800)`가 들어와 최종값이 **top0·height800·z900**이었다. 따라서 파일의 “profile only” 주석은 실제 적용 범위를 보장하지 못한다. 현재 엔진 해시는 `f75032d7…`이다.

이는 파일을 나눠 저장하는 것만으로 화면 scope가 생기지 않는다는 근거다. 신규 규칙은 실제 장면 root 선택자로 제한해야 한다. 해당 테두리의 작은 보완안은 기존 프로필 전용 `#jo9_tv_root::before`로 상단 0~45px만 채우고, base의 45~800px 테두리는 유지하는 방식이다. 새 저장 변수·DOM 상태 플래그·body class 수명 관리가 필요 없다. 실제 프로필·팝업 레이어 검증 후 별도 적용해야 하며 이번 조사에서는 수정하지 않았다.

## 개인실 반복 패턴

`slave_private_room1..4`와 `snk_room_menu_screen`의 inline geometry는 각 22개다. inventory에서 줄 번호와 로케이션명을 제외한 **순서·tag·id·class·geometry가 다섯 곳 모두 완전히 동일**했다. 합계 110개의 반복 태그다.

주요 내용은 34×36 아이콘 4개, 28×30 아이콘 2개, 28×29 아이콘 2개와 `position:relative` 툴팁 앵커다. 방 전체의 절대 좌표가 22개씩 있다는 뜻은 아니다. 우선 공통 CSS의 역할별 아이콘 class로 치수만 공유하는 것이 작은 정리다. 방 번호별 인물 소유권·선택지·복귀 코드를 합칠 이유는 없다. 기존 서로 다른 29/30 높이도 첫 단계에서는 보존한다.

## 저장 변수 없이 운영할 수 있는 규격

1. 개발용 명세에 `canvas1280×800`, 화면 종류, 원점 소유자, root, 배경 영역, 겹쳐도 되는 영역, 메시지 포털을 기록한다. 명세는 빌드·검사용 파일이며 세이브에 넣지 않는다.
2. 신규 markup은 장면 class 하나와 역할 class만 붙인다. 좌표·크기·색·여백은 CSS가 소유하고, QSP는 내용·조건·선택지와 엔진의 본문/메시지 영역 설정만 소유한다. 기존 `CSS_2_4_POLICY_20261015.md`와 같은 구분이다.
3. 오래된 QtWebKit에서 검증하지 않은 CSS 변수·grid에 의존하지 않고, 필요하면 개발 명세에서 평범한 CSS 상수를 생성한다. 새 런타임 함수나 영구 상태는 필수가 아니다.
4. 검사기는 경고와 근거만 내며 자동으로 소스를 고치지 않는다. 공용 ID/전역 body 규칙, 같은 치수의 반복, 그림보다 작은 부모, root 밖의 절대 좌표, 불필요한 stacking context를 정적 후보로 수집한다.
5. 실제 엔진에서는 config UTF-16LE/BOM과 뷰포트부터 검증한 뒤, root·그림 경계 일치, 부모 원점 이동, 본문 배경과의 틈, 긴 글/기술 목록, 최상위 링크/닫기 hit-test를 화면 종류별로 확인한다. 기존 화면은 기준 스냅샷을 보존한다.

안전한 진행 단위는 **새 화면부터 규격 적용 → 반복 아이콘 같은 저위험 공유 → 장면별 검증된 이행**이다. 원본 공통 helper·공용 `#bg`·모든 CSS의 전역 교체는 규칙 통일과 분리해야 한다.
