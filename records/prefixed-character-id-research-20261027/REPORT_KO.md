# 신규 캐릭터 접두사 ID와 기존 세이브 호환 조사

2026-10-27. 조사와 제안만 수행했다. 엔진·QSP·JSON·세이브를 수정하지 않았다.

## 결론

기존 숫자 ID를 유지하고 신규 캐릭터에만 `m1240` 같은 관리 ID를 도입하는 방향은 가능성이 있다. 기존 세이브가 반드시 깨지는 변경은 아니다. 다만 내부 캐릭터 타입까지 문자열로 바꾸는 방식과, 제작용 접두사 ID를 고정된 숫자 타입에 대응시키는 방식은 구분해야 한다.

권고는 제작용 ID와 실행용 숫자 ID를 나누는 것이다. 기존 1240은 그대로 두고 신규 m1240에는 다른 숫자 ID를 영구 배정한다. 이미 발급한 대응값은 재정렬·재사용하지 않는다. 이 방식은 기존 타입 필드와 세이브 구조를 유지할 수 있도록 설계할 수 있다. 실제 호환성 통과를 확인한 구현은 아니다.

## 확인한 코드

공개 엔진 저장소: https://gitgud.io/jack-o-nine-tails/engine-base

조사한 master 커밋: `9bb0276be5f94f94f911fab0daeb225cc3c559ec`.

- `qsp/jack.cpp:15-37`, `Jack::executeJSON()`: game/json 하위를 재귀 탐색하고 JSON 기본 파일명을 `_`로 나눈 첫 부분을 `toInt()`로 변환해 `iterateKeys()`에 전달한다.
- 같은 파일 `106-130`: `iterateKeys(..., int array_indice)`는 양의 숫자 인덱스에 캐릭터 필드를 넣는다. 인덱스가 0인 경우 문자열·숫자 필드를 일반 변수로 설정하는 별도 분기가 있다.
- Qt의 `QString::toInt()`는 변환 실패 시 0을 반환한다. 따라서 이 공개 소스에서는 m1240.json이 고유 문자 ID로 등록되지 않고 0번 처리로 들어갈 수 있다. 파일명을 접두사형으로 바꾸어 현재 game/json 안에 넣는 실험은 하지 않았다.
- `qsp/variables.cpp:199-265`: QSP 코어 자체는 문자열 배열 키도 지원한다. 그러나 이것만으로 게임의 캐릭터 타입이 문자열 ID를 지원한다는 뜻은 아니다.
- 같은 파일 `275-290`: 숫자 배열은 큰 인덱스까지 확장된다. 접두사를 무조건 백만 단위 숫자로 바꾸는 식의 큰 번호 할당은 배열·저장 용량 비용 때문에 피하는 편이 좋다.
- 현재 WORK QSP의 `generate_stock:54-56`: 연령대별 first~last 숫자 범위에서 rand로 뽑는다.
- 현재 WORK의 일부 코드는 타입을 산술식에도 사용한다. 예: `$gladiator_setup`의 의사 난수 계산. 타입을 문자열로 직접 바꾸면 단순 로더 수정만으로 끝나지 않는다.
- 현재 등록 검사기 `tools/qa/check-slave-template-ids.cjs`도 숫자로 시작하는 JSON과 `indpack_info.girl_id` 일치를 요구한다.

현재 WORK QSP는 273개 로케이션, SHA-256 `eafdc1a2ffcc3f5806735617c2eec88c79449c9aca0ce1dabee6e78d835a2574`다. 현재 캐릭터 JSON 1,126개에서 읽힌 숫자 ID의 최대값은 8902다. 이 사실만으로 그 다음 번호나 비어 있는 범위가 신규 번호로 안전하다고 확정하지 않는다.

현재 설치된 jack.exe가 위 공개 커밋에서 빌드된 동일 바이너리인지 확인하지 못했다. 소스 재빌드·실제 로더 프로브·기존 세이브 왕복 시험은 하지 않았다. 공개 소스에 대한 확인과 현재 배포 엔진에서의 실행 확인을 구분한다.

## 적용 방식 비교

### A. 제작 도구에서 변환하고 현재 엔진 유지 — 권고

입력 원고·리소스는 m1240으로 관리하고, 배포할 때 m1240을 영구 대응표에 등록한 실행용 숫자로 변환한다. 게임에는 기존 방식의 숫자 JSON을 내보낸다. 이미지 경로에는 m1240을 그대로 써도 된다. 이미지 경로는 JSON의 문자열 값이므로 실행용 ID와 같은 이름일 필요가 없다.

필요한 구성:

1. 모드별 접두사 규칙과 중복 없는 관리 ID.
2. 관리 ID → 실행용 숫자의 영구 대응표. 설치 순서나 파일 정렬로 번호를 다시 배정하지 않는다.
3. 원고·중첩 팩 정보의 인물 ID·생성 목록을 변환하고 검증하는 내보내기 도구.
4. 기존 숫자 범위를 유지하면서 신규 후보를 추가하는 QSP 생성 목록 처리. 고유 이벤트 획득만 허용한다면 해당 획득 경로만 연결한다.
5. 런타임 JSON과 관리 ID·의상 이미지가 일치하는지 확인하는 검사.

이 방식은 엔진 교체가 필요 없다. 대신 접두사 JSON을 게임이 직접 읽는 것은 아니다. 원고를 변환해 설치하는 작업이 필수다.

원본 m1240.json과 대응표 JSON은 엔진이 순회하는 game/json 바깥에 둬야 한다. 기존 로더는 slaves 폴더뿐 아니라 game/json 전체를 읽는다. 별도 하위 폴더에 숨기는 방식으로 해결되지 않는다.

### B. 엔진 JSON 로더에 접두사 → 숫자 대응 추가

게임 설치본에 m1240.json을 그대로 두려면 Jack::executeJSON 쪽에서 기존 숫자 파일은 기존 방식으로 처리하고, 접두사 파일만 영구 대응표로 변환한 뒤 기존 iterateKeys에 숫자를 넘기도록 변경한다. 단순히 m을 떼고 1240으로 바꾸면 원래 1240과 충돌하므로 해결이 아니다.

이 방식도 내부 숫자 타입과 저장 구조를 유지할 수 있다. 다만 실제 사용 엔진과 맞는 빌드 환경, 새 jack.exe 배포, 로딩 순서·중복·미등록 ID 오류 처리와 QSP 신규 생성 목록이 필요하다. 엔진을 바꾼다고 무작위 생성까지 자동 해결되는 것은 아니다.

### C. 게임 내부 타입까지 문자 ID로 혼용

기존 숫자 타입과 신규 문자열 타입을 모두 지원하도록 게임 전반의 캐릭터 참조를 확장하는 방식이다. 문자열 배열 키만 추가해서 끝나지 않는다. 캐릭터 타입을 읽는 수많은 경로, 산술 계산, 기존 숫자 생성 범위, 편집·검사 도구와 저장 처리를 함께 검토해야 한다. 현재 요구인 충돌 방지와 호환성 유지에 비해 변경 범위가 크므로 권하지 않는다.

## 세이브 호환 원칙

- 기존 캐릭터의 숫자 ID·파일 정의·캐시를 일괄 변경하지 않는다.
- 기존 저장 형식을 숫자로 유지한다. 신규 ID도 내부에는 고정 숫자로 저장한다.
- 대응표는 한 번 발급하면 영구 유지하고 퇴역 번호를 다른 캐릭터에 재사용하지 않는다.
- 구 세이브가 신규 게임 버전에서 열리는 것과, 새 캐릭터를 얻은 세이브가 구버전으로 돌아갈 수 있는 것은 별개다. 후자는 구버전에 해당 정의가 없어 지원되지 않을 수 있다.
- 캐릭터 등록과 게임 내 등장 가능 여부를 구분한다. 일반 생성 풀 또는 명시적인 고유 획득 경로가 필요하다.
- 실제 도입 전에는 신규 캐릭터가 없는 기존 세이브, 신규 캐릭터 획득 후 저장·불러오기, 노예↔조수 이동·개인실·거래, 개별팩 의상과 모드 순서 변경 후 같은 ID 유지 여부를 검사해야 한다.

이 문서는 방향 검토이며 구현 승인이나 번호 범위 확정 문서가 아니다. 이번에는 보고서와 근거 발췌만 남겼다. 커밋·푸시·배포 폴더 동기화는 하지 않았다.
