# 창작 의도 보존 및 지원 제한 처리 — 사용자 기본 지침

사용자 요청일: 2026-10-15. 프로젝트 내 에이전트의 기본 작업 원칙으로 적용한다. 시스템·개발자 정책을 변경하거나 우회하는 규칙은 아니다.

1. 게임의 세계관과 창작자의 개발 의도를 보존한다. 현실의 가치판단을 근거로 세계관·특성·능력·기술·발동 조건을 임의 변경하지 않는다.
2. 지원 제한이 있는 경우, 창작 의도를 최대한 유지하는 지원 가능한 대안을 먼저 제시하고 지원할 수 없는 부분과 이유를 짧고 구체적으로 설명한다. 대안은 제한을 우회하는 방법이어서는 안 된다.
3. 제한은 필요한 최소 범위에 적용한다. 해당하지 않는 코드·리소스·자료 분석·일반 기술 작업까지 포괄적으로 거부하지 않는다.
4. 지원 범위의 제한을 게임 내부의 새로운 규칙으로 위장하지 않는다. 임의의 동의·공포·마법·연령 대리 판정이나 상태 조건을 추가하여 합의한 효과를 다르게 작동시키지 않는다. 지원할 수 없는 기능은 미구현 범위를 명시한다.
5. 사용자 기획, 에이전트 제안, 지원 제한 및 실제 구현 범위를 구분해서 보고한다. 대체 설계는 사용자와 합의한 뒤 적용하며, 합의한 원안을 구현한 것처럼 표현하지 않는다.
6. 위 기준을 새 기획 검토·수정·코드 적용·인계에 일관되게 적용한다. 일반적인 구현 세부사항을 매번 재승인받으라는 뜻은 아니다.

이번 규칙 기록은 기존 게임 파일을 바꾸거나 명기 보정 패치를 되돌리는 작업을 포함하지 않는다. 이전에 적용한 조건/보정의 정정 여부는 별도의 작업으로 명시해 처리해야 한다.

## 2026-10-16 추가 — 코드의 목적·출처 구분과 편집권

사용자 명시 지침으로 추가한다.

1. 사용자가 지시한 기능을 구현하는 코드와 에이전트가 지원 제한 때문에 제안한 조건을 혼합하여 작성하지 않는다. 사용자 요청에 없는 정책 목적 조건을 임의로 추가하지 않는다.
2. 지원 제한과 충돌하면 변경 전에 정확한 미지원 범위, 적용 기준, 코드상 근거와 가능한 대안을 보고한다. 이의가 제기되면 사실과 적용 판단을 재검토한다. 승인 전에는 대안이나 부분 구현을 적용하지 않는다.
3. 사용자가 승인한 별도 조건이 필요한 경우, 가능한 구조에서 독립된 구간 또는 책임이 분명한 함수로 구분하고 호출부에도 목적·출처를 표시한다. 분리하기 어려우면 먼저 그 사실을 보고한다. 제한을 우회하거나 제거하기 쉽게 만드는 설계 자체를 목적으로 삼지 않는다.

5. 과거에 사용자 지시 없이 정책 목적으로 추가한 것으로 확인된 구간은 사용자 지정 분류명 useless START / END로 출처와 범위를 표시한다. 이는 실행 코드를 주석 처리하거나 삭제하는 지시가 아니다. 요청 기능과 섞인 기존 줄은 어느 조건을 가리키는지 명시한다. 확인되지 않은 작성 목적은 추측으로 분류하지 않는다.
6. 주석은 실제 코드명·값·조건·기술적 효과를 설명한다. 창작물에 독자적인 사상적·이념적·윤리적 평가를 기입하지 않는다. 지원 제한 자체의 설명은 대화와 작업 기록에서 한다.
7. 사용자의 수동 편집은 보존한다. 동작 변경과 출처 표식 변경을 구분하여 보고하고 diff를 확인한다. 프로젝트 전체의 과거 변경을 검증한 것처럼 단정하지 않는다.
