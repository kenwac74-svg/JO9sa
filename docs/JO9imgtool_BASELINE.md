## 3. 사용자 확정 정책: 기존 이미지 백업·복구 유지

**이전에 정한 무백업 정책은 사용자가 명시적으로 철회했다. 현재 구현된 이미지 백업과 복구 기능을 유지한다.**

- 교체 전 원본 이미지의 백업본을 생성·보관하는 기존 절차를 유지한다.
- 기존 ‘백업 후 교체’, 백업 기록, 이미지 복구 및 교체 실패 시 복구 처리와 관련 검증을 제거하지 않는다.
- 이미지 백업 관련 버튼·안내·필수 의존성을 제거하거나 우회하는 작업은 하지 않는다. 백업 기능 제거는 더 이상 개발 과제가 아니다.
- 사용자가 직접 선택한 이미지라는 이유로 백업을 생략하지 않는다. 입력 이미지·대상 경로·쓰기 권한·변경 감지 등 기존 검증과 오류 처리를 유지한다.
- 완성된 이미지의 PNG/ZIP 내보내기는 결과물 저장이며, 교체 전 원본의 백업과 구분한다.
- 기존 백업 파일을 삭제하지 않는다. 보관 기한·자동 삭제·백업 범위 확대 등의 새 정책은 이번 결정에 포함하지 않는다.

현재 배포본의 이미지 백업 호출·버튼·안내·복구 루틴은 모두 유지 대상이다. 이전 무백업 정책을 근거로 제거하지 않는다.

## 6. 다음 업데이트: 이벤트 컷신 전용 이미지 및 연결 경로 변경

**상태: 개발 전 단계. 이번에는 요구사항과 확인 항목만 기록한다. 구현·게임 적용·배포를 시작하지 않는다. 이 일정과 범위는 무백업 정책 철회와 무관하게 유지한다.**

이 기능은 기존 이미지 파일 교체와 별개로, 선택한 이벤트 컷신이 다른 이미지 경로를 사용하도록 실행용 QSP를 수정하는 업데이트다.

- 기존 Show HTML 자동감지와 이미지 편집 UX를 재사용한다. 추가하는 핵심은 이미지 감지가 아니라 이벤트 한정 적용 방식이다.

- HTML 미리보기의 경로만 바뀌거나 `.qsrc` 수정본만 생성된 상태를 게임 적용 완료라고 표시하지 않는다. 실행용 QSP 반영과 실제 이벤트 재진입 검증을 별도로 구분한다.

### 첫 대상: 부동산 NPC

사용자 설명 기준으로 부동산 상점은 한 곳이며 NPC는 그 상점에만 등장한다. 구매 완료 분기에서 해당 컷신이 발생할 때는 같은 장면을 사용한다. 이는 노예가 아니라 고정 NPC이므로 `slave id`를 요구하거나 노예 데이터 등록을 전제하지 않는다.

대상은 부동산 구매 완료 이벤트의 해당 컷신으로 잡되, 실제 소스에서 호출 범위와 분기를 확인하기 전까지 특정 코드가 이 NPC 전용이라고 단정하지 않는다. Show HTML로 감지한 이미지 경로만으로 이벤트 ID나 QSP 조건문을 모두 알 수 있다고 가정하지 않는다.

## 8. 다음 패키징부터 적용할 ZIP 구조

**ZIP 안에는 프로그램명과 실제 배포 버전을 포함한 최상위 폴더를 하나만 둔다. 모든 파일과 하위 폴더는 그 안에 배치한다.** 사용자가 압축을 풀었을 때 프로그램·버전별로 구분되며 파일이 바깥에 흩어지지 않게 한다.

- 최상위 폴더명 형식: `JO9_ImageWorkshop_v<배포 버전>`.
- 예시: `JO9_ImageWorkshop_v1.1.2/`. 이 번호는 구조 예시이며, 차기 배포에서는 실제 버전·필요한 리비전 표기와 일치시킨다.
- 설치 관리자, `payload/`, `docs/`, README, 상태 안내, 검증 기록, 숨김 관리 파일 등 패키지에 포함하는 모든 항목을 단일 최상위 폴더 아래에 둔다. 그 밖에 별도 파일을 놓지 않는다.
- 내부의 기존 파일 간 상대경로와 `payload` 구조는 유지한다. 최상위 폴더를 불필요하게 두 겹으로 중첩하지 않는다.

```text
JO9_ImageWorkshop_v1.1.2.zip
└─ JO9_ImageWorkshop_v1.1.2/
   ├─ JO9_PATCH_MANAGER.cmd
   ├─ JO9_PATCH_MANAGER.ps1
   ├─ payload/
   ├─ docs/
   └─ 기타 안내·설정·관리 파일
```

패키지 폴더는 그대로 유지한 채 그 안의 설치 관리자를 실행하도록 한다. 게임 루트 판별은 다음 절의 방식으로 바꾸며, 파일을 게임 루트로 다시 꺼내 놓는 절차를 사용자에게 요구하지 않는다. 다음 패키징 시 경로 탐색 로직과 설치 안내를 함께 반영·검증한다. 폴더를 한 겹 추가한 사실만으로 설치 동작까지 검증했다고 표시하지 않는다.

이번에는 다음 패키징 규칙만 기록한다. 이미 제공한 ZIP을 재생성하거나 저장소의 기준본 작업 폴더를 이동하지 않는다. 기존 이미지 백업·복구 유지 및 QSP 기능의 개발 전 단계라는 상태도 바꾸지 않는다.

## 9. 다음 패키지의 게임 경로 탐색·직접 선택

**게임 루트에서 설치기를 실행하도록 요구하지 않는다. 패키지 폴더에서 실행하고, 한 단계 상위 폴더의 `Jack-o-nine-tails.exe`를 우선 찾는다. 없으면 사용자가 파일 선택 창에서 해당 실행 파일을 직접 선택한다.**

기본 배치 예시:

```text
게임 폴더/
├─ Jack-o-nine-tails.exe
└─ JO9_ImageWorkshop_v1.1.2/
   ├─ JO9_PATCH_MANAGER.cmd
   ├─ JO9_PATCH_MANAGER.ps1
   ├─ payload/
   └─ docs/
```

- 탐색 기준은 설치 관리자 파일이 있는 패키지 폴더다. 콘솔의 현재 작업 폴더나 바로가기의 시작 위치를 기준으로 삼지 않는다.
- 자동 탐색은 패키지 폴더의 부모 폴더에 있는 `Jack-o-nine-tails.exe`를 확인한다. 드라이브 전체나 여러 단계 상위 폴더를 재귀 탐색하는 기능을 추가하지 않는다.
- 찾지 못하면 ‘Jack-o-nine-tails.exe를 선택하세요’라는 파일 선택 창을 제공한다. 사용자가 선택한 실행 파일의 부모 폴더를 게임 루트로 사용한다. 경로를 직접 타이핑하거나 패키지를 옮기도록 강요하지 않는다.
- 자동/수동으로 찾은 실행 파일의 존재와 이름, 기존 설치기의 게임 구조·호환성 조건을 확인한다. 잘못된 파일은 재선택하도록 안내하고, 선택 취소 시 파일을 변경하지 않고 중단한다.
- 패키지 소스 경로와 게임 설치 대상 경로를 분리한다. `payload`는 패키지 폴더에서 읽고, 설치·검증·삭제·설치 복구 및 관련 게임/서버 제어에는 확인된 게임 루트를 일관되게 전달한다. 각 하위 스크립트가 자기 위치에서 게임 루트를 다시 추정하게 두지 않는다.
- 적용 대상 게임 경로를 변경 작업 전에 표시하며, 기존 설치 확인·백업·복구 검증을 유지한다. 설치용 실행 파일 선택은 기존 이미지편집기의 PIC 폴더 등록 UX를 없앤다는 뜻이 아니다.
- 다음 패키징 검증에는 부모 폴더 자동 발견, 다른 위치의 게임 수동 선택, 한글·공백 경로, 잘못된 파일·선택 취소, 설치·검증·삭제의 동일 대상 사용을 포함한다.

이 절은 다음 패키지에 반영할 설치 경로 처리 요구사항이다. 현재 기준본/기존 ZIP의 설치기가 이미 이 방식으로 작동한다고 주장하지 않는다. 이번에는 문서만 수정하며, QSP 관련 기능은 계속 개발 전 단계로 유지한다.
