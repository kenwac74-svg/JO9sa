## 구매자 요구판정: 실제 구조

고객 정의의 $buyer_demand[고객ID]는 요구 데이터를 만들고, slave_sell_chek가 그 데이터를 읽어 거절 여부를 결정한다. $npc_preferences[고객ID]는 능력·기술 요구인 stat_importance를 만든다. 데이터에 키가 있다는 사실만으로 검사가 자동 실행되지는 않는다.

1. slave_sell_chek가 관심 여부와 임시 능력 요구를 초기화하고 $slave_price로 현재 등급/가격을 계산한다. 요구 등급 미달이면 sl_txt=101로 즉시 종료한다.
2. demand를 초기화하고 고객별 $buyer_demand를 실행한다. 연령·마녀 제외·일부 특성·낙인/문신·외모/체형 등의 명시된 검사문을 수행한다.
3. 상처·에너지·지구력·회복 상태·공개된 임신·청결·매력을 검사한다. 가문 구매 경로에서는 매력 일부를 앞에서 검사한다.
4. $npc_preferences를 실행한 뒤 stat_importance의 일반 능력·직업·기술 요구를 검사한다. 이 경로의 부족은 sl_txt=102다.
5. 성공한 경우 관심 플래그를 세우고, 호출한 판매 경로가 금액 지급·인물 이동/제거·진행도·평판을 처리한다. 일반 흥정 경로와 sell_slave_complex 직납품 경로는 처리 방식이 다르다. 모든 판매가 같은 검사기를 통과한다고 가정하지 않는다.

주요 결과 코드는 100=개별 요구 거절, 101=등급 미달, 102=기술/능력 미달, 103=청결/매력, 104=건강/회복, 105=공개된 임신이다. 현재 화면은 개별 검사에서 만든 $refuse_txt를 항상 직접 보여 주지 않고 일반 거절 문구 또는 고객별 $refuse_special_quote를 쓴다. 조건이 틀린 것과 거절 이유가 자세히 표시되지 않는 것은 별도 문제다.

### 확인된 누락과 그 범위

사용자 지시로 **여성 주인공용 #npc_base_woman 정의를 제외**한다. 주석 처리된 요구 대입도 활성 등록으로 세지 않는다. RM 공통 검사에만 있는 키 25개 중 현재 남성 주인공용 활성 정의에 등록된 것은 **13종**이다. 이는 13개 고객이나 확정 버그 13건이라는 뜻이 아니다.

앞선 20종은 여성 주인공용 정의를 포함한 수치였다. 초기 연결표에는 일부 주석 처리된 남성용 대입도 표시됐으므로 이번 표에서 제외·정정했다. 조건을 주석으로 끈 항목은 의도된 제외일 수 있어 자동 복구하지 않는다.

**판단 방식:** 코드 대조로 검사 누락·값 미설정 여부를 확인할 수 있다. 그러나 누락 자체가 의도된 완화인지까지는 요구 대사·주석·변경 이력·개별 경로를 함께 봐야 한다. 플레이는 조건을 바꾼 전후에 실제 인수/거절·금액·진행이 예상대로 변하는지 검증한다. 플레이만으로 원작자의 의도를 확정할 수는 없다. 다음 수정은 확정된 기술 오류와 기획 판단이 필요한 항목을 분리한다.

### 레시: 실제 연결을 확인한 예

- #npc_base 3197의 요구 등급은 6(B+). 3219~3224에는 지성·자아·간호·검투 4, 마법 5, 특수 적응 기술 5의 대입이 있다. 이 값들은 공통 검사기의 대응 항목에서 실제 검사한다.
- 같은 정의 3228의 demand['unknown']=1은 등록되지만, 현행 검사기에 명성을 비교하는 unknown 조건이 없다. 따라서 다른 조건을 통과하면 유명한 인물이라는 이유만으로는 이 판매가 거절되지 않는다.
- 3229의 demand['min_sensitivity']=1도 검사기가 없다. 더구나 3218의 stat_importance['sensitivity'] < 4는 대입이 아닌 비교식이어서 감수성 요구값을 설정하지 않는다.
- 3227의 demand['min_stamina'] > 3도 대입이 아닌 비교식이다. 현재 일반 건강 검사인 지구력 2 미만 거절과 레시 고유의 지구력 요구는 같은 것이 아니다.
- 메뉴 #options 4438~4441 → interaction_city 12035 → 120352 → sell_slave_complex → interaction_result_city 166~167의 slave_sell_chek 호출로 연결된다. 해당 분기에는 unknown을 대체하는 명성 검사도 없다.

따라서 레시 의뢰가 정상적으로 끝난다는 사용자 확인과 모순되지 않는다. **완료/복귀가 정상인 것**과 **말한 요구를 전부 검사하는 것**은 다른 검증이다. 이번 조사에서는 판매 성공 재현 세이브를 조작하거나 게임을 실행하지 않았다.

### RM을 그대로 복사하면 안 되는 이유

- RM의 min_sensitivity는 sensitivity > 3일 때 거절하면서 문구는 감수성 부족이라고 한다. 이름·문구·비교 방향이 일치하지 않는다. 레시의 낮은 감수성 취향인지, 다른 고객의 최소값인지 요구 대사와 구분해야 한다. 현행 poison은 같은 키에 3을 넣지만 RM 검사는 =1만 검사하므로 그것도 그대로 처리하지 못한다.
- RM anal_pure는 내부 END 뒤에 거절 문구와 exit가 붙어 있어 바깥 조건이 켜지면 내부 검사 결과와 무관하게 종료될 가능성이 있다.
- RM nopreversion/preversion 표기 혼재와 fertility의 공개 여부 조건도 확인이 필요하다. 잘못된 이름에 맞춰 새 변수를 만들지 않는다.

수정한다면 고객별 요구 대사 → 실제 등록 값 → 검사 → 거절/인수 → 금액/진행 보존 순으로 연결표를 확정하고, 맞음/틀림/정보 미공개를 나눈다. 이는 이번에 적용한 수정이 아니라 다음 수정의 검증 기준이다.
