## 최소 컨텍스트

- 초기 조사 범위는 가능하면 5\~10개 관련 파일 또는 관련 QSP location 수준으로 제한한다.

# 4. JO9 원본과 모드 분리

원본 게임과 사용자 모드를 명확히 구분한다.

가능하면:
```
원본 게임 파일
↓
분석 대상

SNKmod / 사용자 모드 파일
↓
실제 수정 대상
```

구조를 우선한다.

원본을 직접 수정해야 하는 작업인지, 모드 경로 변경으로 해결할 수 있는지 먼저 판단한다.

기존 사용자 방침상 UI/UX 관련 자산은 가능한 경우 모드 전용 경로에서 관리하는 구조를 우선 고려한다.

원본 교체가 필요한 자산과 경로 변경이 가능한 자산을 혼동하지 않는다.

# 5. 이미지 관련 작업

이미지 파일은 컨텍스트 비용이 크므로 무차별 탐색하지 않는다.

우선:

1. 이미지 파일명 검색
2. QSP/HTML에서 호출 위치 검색
3. 실제 사용 location 확인
4. 필요한 이미지만 열기

순으로 진행한다.

같은 파일명이 여러 폴더에 존재할 경우 임의로 하나를 기준본으로 결정하지 않는다.

다음을 먼저 확인한다.

- 실제 게임에서 사용되는 경로
- 완전히 동일한 복제 파일인지
- 이름만 같고 내용이 다른 파일인지
- 사용되지 않는 잔존 파일인지

판단이 필요한 경우 사용자에게 결과를 명확히 알려야 한다.

# 6. QSP 분석 원칙

QSP 관련 질문에서는 전체 디컴파일 결과를 처음부터 읽지 않는다.

우선 다음으로 범위를 찾는다.
```
location명
표시 문자열
변수명
이미지 파일명
버튼/링크 텍스트
이벤트 이름
NPC 이름
조건문 키워드
```

그 후 해당 location과 직접 호출 관계만 읽는다.

필요할 경우:
```
호출자
→ 대상 location
→ 직접 관련 변수
```

순으로 확장한다.

질문의 답을 찾은 후 관계없는 다른 location 분석을 계속하지 않는다.

# 10. 실패 처리

같은 방법이 실패했다고 동일 작업을 그대로 반복하지 않는다.

기본:
```
실패
→ 첫 실제 오류/잘못된 동작 확인
→ 원인 범위 축소
→ 관련 QSP/코드/경로만 확인
→ 수정
→ 제한된 검증
→ 재실행
```

동일한 접근이 약 2회 실패하면 더 많은 파일과 더 강한 추론을 투입하기 전에 다음을 재검토한다.

1. 찾고 있는 location이 맞는가?
2. 파일명이 동일한 다른 자산을 보고 있는가?
3. 실제로 사용되지 않는 구버전 파일을 분석 중인가?
4. 원본과 모드 경로를 혼동했는가?
5. 현재 브랜치가 맞는가?
6. QSP 호출 구조에 대한 최초 가정이 잘못되었는가?
7. 사용자가 말한 게임 버전과 분석 중인 소스 버전이 일치하는가?

잘못된 전제를 유지한 채 추론량만 늘리지 않는다.

# 11. 모델 라우팅

기본 개발/분석 모델은 **Sol**이다.

모델 차이가 실제 작업 품질이나 비용에 의미가 있을 때만 첫 응답에서 한 줄 추천한다.

추천만 하고 현재 작업은 계속한다.

## 저비용 모델에 적합

- 파일명 검색
- 문자열 검색
- 이미지 경로 검색
- 단순 QSP location 찾기
- 반복적인 파일 분류
- 단순 Git 작업
- 문서 정리
- 이미 정해진 절차 실행

## Sol에 적합

- 일반 QSP 분석
- UI 수정
- 이미지툴 기능 구현
- 일반 모딩
- 이벤트 조건 분석
- HTML/JS/Python 수정
- 일반 버그 수정
- 코드 리뷰
- 다중 파일 수정
- 기존 구조를 이해한 상태의 기능 추가

## Astra 고려

다음 상황에서만 추천한다.

- JO9 전체 모딩 아키텍처를 새로 설계
- QSP / HTML / 이미지 시스템 / 모드 경로가 함께 얽힌 복합 문제
- 기존 접근 자체가 잘못되었을 가능성이 높은 문제
- Sol에서 합리적인 접근을 했지만 핵심 원인을 찾지 못함
- 게임 전체 구조에 영향을 주는 대규모 시스템 변경
- 복수의 모드가 서로 충돌하는 구조를 재설계
- 큰 규모의 QSP 구조 변경 또는 마이그레이션

다음은 Astra 선택 이유가 아니다.

- QSP 파일이 큼
- 이미지가 많음
- 저장소가 큼
- 작업 시간이 오래 걸림
- 파일이 여러 개임

이 경우 먼저 TASK를 줄이고 검색으로 범위를 좁힌다.

**작은 관련 컨텍스트 + Sol을 큰 전체 컨텍스트 + Astra보다 우선한다.**

# 15. Git 반영

현재 JO9 저장소의 올바른 브랜치와 상태를 확인한 뒤:
```
AGENTS.md
AI_CONTEXT.md
CURRENT_STATE.md
```

를 추가 또는 통합한다.

기존 규칙을 무작정 덮어쓰지 않는다.

운영 문서 변경이 현재 브랜치 공통으로 사용되어야 하는 구조라면 저장소 구조를 확인하여 가장 적절한 위치에 둔다.

적절하면 커밋한다.

예:
```yaml
chore: add AI development workflow
```

원격 GitHub push 권한과 현재 작업 흐름이 허용되면 원격 저장소에도 반영한다.

게임 코드나 모드 기능 자체를 이 핸드오프 적용 과정에서 불필요하게 변경하지 않는다.

---

# 16. 이후 운영 책임

이후 JO9 작업에서는 사용자가 매번 다음을 다시 설명하지 않도록 한다.

- 토큰 절약
- 최소 파일 탐색
- 모델 선택
- 브랜치 분리
- QSP 검색 우선
- 이미지 경로 조사 방식
- 실패 시 전제 재검토

AI가 필요할 때 `CURRENT_STATE.md`를 최신 상태로 정리한다.

`AGENTS.md`와 `AI_CONTEXT.md`가 비대해지면 불필요하거나 오래된 내용을 제거한다.

현재 작업과 관계없는 과거 프로젝트 정보를 상시 컨텍스트로 유지하지 않는다.
