### 2. 답변 · 턴 91afccc7-9996-4651-8a7b-f6ea8f307c0e

아니다. **현재 원작 개인실의 일반식/고열량식은 메인 UI 식사 시스템처럼 식비나 식재료를 차감하지 않는다.**

개인실 코드를 보면 일반식과 고열량식은 `room1['calories']`만 계산한다.

```qsp
! 일반식
if room1['fat'] > 1: room1['calories'] = -6
if room1['fat'] = 0: room1['calories'] = 6
if room1['fat'] = 1: room1['calories'] = 3
if room1['neg_hungry'] > 0:
    room1['calories'] += room1['stamina']

! 고열량식
room1['calories'] = 6 + room1['lactation']
if room1['neg_hungry'] > 0:
    room1['calories'] += room1['stamina']
```

여기에는 `total_food_cost`, `slave_food_cost`, `cooked_food` 또는 식재료 재고 차감이 없다. 기존 촉수 식단만 `spawn_semen`을 실제로 차감한다. 

반면 **메인 UI의 일반 노예 식사 시스템은 실제 비용 계산을 한다.** 먹는 양 `eaten_food`를 구한 뒤 음식 종류에 따라:

```qsp
slave_food_cost = 0

! 일반 보존식
if diet_food_type = 0:
    slave_food_cost = eaten_food

! 신선식
if diet_food_type = 1:
    slave_food_cost = eaten_food + eaten_food/2

...

total_food_cost += slave_food_cost / 3
```

처럼 가구 식비인 `total_food_cost`에 합산한다. 영양사나 보충제를 쓰면 추가 식비도 붙는다. 

또 `cooked_food`가 있으면 남은 음식을 먹는 효과도 따로 연동돼 있다. 즉 **메인 식사 시스템은 음식/식비 시스템과 연결돼 있지만 개인실 식단은 그 부분에서 떨어져 있다.** 

그래서 지금 우리가 정한 공식을 그대로 구현하면 이상한 점이 하나 생긴다.

> **일반식 = 무료**  
> **고열량식 = 무료**  
> **특별식단 = 10 스파크/일**

이 된다.

그리고 정확히 말하면 메인 UI도 단순히 “식료품 아이템 1개 감소” 방식은 아니다. 일반 노예 식사는 주로 **먹은 양을 `total_food_cost`라는 스파크 비용으로 환산**하고, 요리된 음식은 별도로 주방 식재료 시스템과 연결된다. 주인 식사도 조리 음식이 없으면 하루 2스파크를 식비에 추가한다. 

따라서 **개인실 개편에서는 일반식·고열량식도 메인 식비 시스템에 연결하는 것이 자연스럽다.** 현재 원작 개인실이 무료로 먹는 것은 기능 누락에 가까워 보인다. 특별식단만 10스파크를 내게 하면 밸런스가 이상해진다.

### 4. 답변 · 턴 c3444a0c-cff1-4b92-8b31-62eee4d8ac6a

게임 내부 가격을 기준으로 다시 맞추면 **일반식 2 / 고열량식 4 / 특별식단 8 스파크/일**이 가장 자연스럽다.

원작 메인 식단의 가격 기준이 이미 꽤 명확하다. B+ 체력의 보통 급식 기준 건조식은 약 **2스파크/일**, 신선식은 **3스파크/일**로 주석에 직접 명시되어 있고, 외부에서 전량 구입하는 고비용 식품은 **6스파크/일** 수준이다. 식비는 최종적으로 `total_food_cost`에 누적된다.  영양사 식단은 여기에 **+5스파크/일**, 보충제는 **+1스파크/일**이 추가된다.  주인공의 평범한 통조림 식사도 조리 음식이 없으면 **2스파크/일**이다. 

| 개인실 식단 | 제안 일 비용 | 산정 근거 |
|---|---:|---|
| **일반식** | **2** | 원작 보통 건조식 2/day와 동일. 개인실이라고 기본 생존식 자체에 프리미엄을 붙이지 않음 |
| **고열량식** | **4** | 신선식 3보다 한 단계 비싸게. `6 + lactation` 칼로리 공급과 체중 증가 목적에 대한 추가 1 |
| **특별식단** | **8** | 신선식 3 + 영양사 관리 5 = 정확히 8. 음식뿐 아니라 장기적인 `pos_cookie / pos_dessert` 특별대우 효과까지 포함 |

특별식단을 전에 잡았던 **10스파크/일은 원작 경제 기준으로 보면 조금 비싸다.** 원작에는 다크초콜릿 1, 케이크 2, 바나나 선데이 4, 행복 젤리 8, 암브로시아 25라는 보상 가격대가 있다. 특히 행복 젤리가 8스파크다.  특별식단은 매일 지불하고 5일·10일을 유지해야 효과가 올라가기 때문에 8스파크만 해도 **5일 40 / 10일 80 스파크**가 든다. 여기에 장기 공급 시 `spoil` 페널티까지 있으므로 10까지 올릴 필요는 크지 않다.

또 특별식단의 `pos_cookie`와 `pos_dessert`는 원작에서 실제 긍정 moodlet으로 쓰이는 값이다. `pos_cookie`는 좋은 음식을 먹었다는 만족, `pos_dessert`는 달콤한 간식에 대한 만족을 나타낸다. 

비용 처리도 원작과 맞추려면 즉시

```qsp
sparks -= 8
```

보다는 **일일 결산에서**

```qsp
if roomX_ration = NORMAL:
    total_food_cost += 2

elseif roomX_ration = HIGH_CALORIE:
    total_food_cost += 4

elseif roomX_ration = SPECIAL:
    total_food_cost += 8
end
```

처럼 `total_food_cost`에 넣는 쪽이 낫다. 원작 노예 음식비도 이 계정으로 누적하고, 영양사 비용 역시 “decade end”에 청구되는 식비라고 코드 주석에 명시되어 있다. 

따라서 **가격 공식 확정안은 `2 / 4 / 8`**을 권한다.

4개 개인실을 전부 같은 식단으로 돌릴 경우에도 균형이 깔끔하다: 일반식은 하루 8, 고열량식 16, 특별식단 32스파크이고, 10일 기준 각각 **80 / 160 / 320스파크**다. 특별대우를 4명에게 계속 제공하면 확실히 유지비가 느껴지지만 감당 불가능한 수준은 아니다.

### 8. 답변 · 턴 42f4299b-1575-4a24-b9af-3791edd4e518

그 문구는 **기존 저장파일에 이미 들어 있는 `roomX_ration` 숫자의 의미가 새 패치에서 바뀌기 때문**에 넣은 안전장치다.

현재 원작 값은 대략 이렇다.

```text
-1 = 굶김
 0 = 고열량식
 1 = 일반식
 2 = 촉수 산란액 식단
```

그런데 새 기획은:

```text
0 = 고열량식
1 = 일반식
2 = 특별식단
```

으로 `2`를 재사용하려고 한다.

예를 들어 예전 세이브에서 Jasmine이 `room1_ration = 2`였다고 하자. 그 세이브에서는 **촉수 산란액 식단을 먹던 상태**다. 그런데 패치 후 그대로 불러오면 코드가 같은 숫자 `2`를 **특별식단**으로 해석해서 갑자기:

```text
8 스파크/일 식비
special_diet_days 증가
5일 후 pos_cookie
10일 후 pos_dessert
spoil 증가
```

가 시작될 수 있다.

`-1`도 마찬가지다. 새 UI에서는 굶기 옵션을 없앴는데 과거 세이브에:

```text
room3_ration = -1
```

이 남아 있으면, 화면에는 굶기 선택지가 없는데 내부적으로는 계속 굶고 있는 이상한 상태가 될 수 있다.

그래서 내가 문서에 쓴

> **임의 마이그레이션 금지, QA 필요**

라는 말은:

> 개발 AI가 자기 판단으로 기존 세이브의 `-1`과 `2`를 아무 값으로 바꾸지 말고, 우리가 **구세이브를 어떻게 변환할지 규칙을 먼저 정한 뒤 구현하라**

는 뜻이다.

나는 지금 기준이라면 규칙을 아예 정해버리는 게 낫다고 본다.

```text
구세이브 -1(굶김)        → 1(일반식)
구세이브  0(고열량식)    → 0 유지
구세이브  1(일반식)      → 1 유지
구세이브  2(촉수 산란액) → 1(일반식)
```

특히 기존 `2`를 새 `2=특별식단`으로 그대로 두면 **사용자가 선택하지 않은 유료 특별식단이 자동으로 켜지는 문제**가 생기므로, `1=일반식`으로 변환하는 게 안전하다.

그리고 **새 패치 적용 후 사용자가 직접 특별식단을 선택했을 때만 `2`가 특별식단 의미를 갖게 하는 것**이 가장 깔끔하다.

따라서 이 규칙으로 확정한다면 문서의 “QA 필요”라는 애매한 문구는 지우고 **구세이브 변환 규칙까지 명시**하면 된다.

### 10. 답변 · 턴 0ecf1135-7235-4bff-aa04-55d4ca6aad64

좋다. 그 규칙으로 확정한다.

구세이브 마이그레이션은 다음으로 채택:

```text
구세이브 -1 (굶김)        → 1 (일반식)
구세이브  0 (고열량식)    → 0 유지
구세이브  1 (일반식)      → 1 유지
구세이브  2 (촉수 산란액) → 1 (일반식)
```

그리고 **패치 적용 후 사용자가 직접 특별식단을 선택한 경우에만 `roomX_ration = 2`를 특별식단으로 사용**한다.

핵심 목적은 두 가지다.

- 기존 세이브에서 굶김/촉수 식단이 새 시스템에 잘못 이어지는 것 방지
- 구세이브의 `2`가 자동으로 **8 스파크/일 특별식단**으로 변환되는 것 방지

앞으로 개인실 식단 기획에서는 이 규칙을 **확정 사양**으로 취급하겠다.
