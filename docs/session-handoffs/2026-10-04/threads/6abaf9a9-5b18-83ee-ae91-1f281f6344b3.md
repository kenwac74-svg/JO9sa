# 3-B. 모딩 자산 관리 및 인물 Asset Registry

## 3-B.1 목적

JO9의 등장인물과 관련 자산은 항상 동일한 이름으로 관리되지 않는다.

대표적인 사례가 **Gloria**이다.

게임 내에서는 다음과 같은 서로 다른 식별자가 사용될 수 있다.

```text
인물 고유 이름:
Gloria

역할/대명사:
부동산 관리인
realtor

이미지:
realtor.png

게임 대사 출력:
Gloria: "..."
```

따라서 단순히 `Gloria`라는 문자열을 전체 게임 폴더에서 검색하는 것만으로는 해당 인물의 모든 자산을 발견할 수 없다.

JO9 Workshop에는 이러한 관계를 지속적으로 기록할 수 있는 **Asset Registry**를 둔다.

목표:

> 하나의 인물 이름으로 검색하면 자동으로 발견된 자산과 사용자가 직접 연결한 자산, 그리고 아직 게임에 적용하지 않은 제작 중 자산까지 함께 확인할 수 있게 한다.

---

# 3-B.2 별도 기능으로 분리

Asset Registry는 Text Workshop 자체의 기능으로 취급하지 않는다.

다음 기능들과 병렬 관계를 가진 독립 모듈이다.

```text
JO9 Workshop

├─ 이미지 편집
├─ 텍스트 편집
├─ 모딩 자산 관리
├─ 패치 / 변경 기록
└─ 고급 소스 편집
```

엔진 메뉴에서 직접 진입할 수도 있고:

```text
[ 현재 화면 이미지 편집 ]
[ 현재 화면 텍스트 편집 ]
[ 인물 / 모딩 자산 관리 ]
[ 패치 / 복구 ]
```

통합 HTML을 사용할 경우 시작 화면에서 분기할 수도 있다.

```text
JO9 Workshop

[이미지]
[텍스트]
[모딩 자산]
[패치/복구]
```

구체적인 메뉴 배치는 구현 단계에서 조정할 수 있으나 **논리적인 기능은 반드시 분리한다.**

---

# 3-B.3 Asset Entity

Asset Registry는 인물을 하나의 **Entity**로 등록한다.

예:

```text
Entity
────────────────────
표시 이름: Gloria
분류: 고유 NPC
내부 ID: gloria
────────────────────
```

Entity는 단순한 문자열 검색어가 아니다.

하나의 Entity에는 여러 식별자와 여러 종류의 자산을 연결할 수 있다.

---

# 3-B.4 Alias

같은 인물을 가리키는 다른 표현을 Alias로 등록한다.

Gloria 예:

```text
Gloria

Aliases:
- Gloria
- 글로리아
- realtor
- 부동산 관리인
```

단, Alias가 있다고 해서 해당 문자열이 등장하는 모든 곳을 자동으로 Gloria와 연결하지 않는다.

예를 들어 `realtor`라는 단어가 여러 이벤트에서 일반 명사로 사용될 가능성이 있기 때문이다.

Alias의 목적은:

```text
검색 후보 확대
+
관련 자산 발견 보조
```

이다.

최종 연결은 Asset Link를 통해 관리한다.

---

# 3-B.5 Asset Link

특정 파일, 텍스트, Location 또는 기타 자산을 Entity에 연결할 수 있다.

예:

```text
Gloria
│
├─ Image
│   └─ realtor.png
│
├─ Event
│   └─ real_estate_event
│
├─ Text
│   ├─ "Gloria..."
│   └─ "부동산 관리인이..."
│
└─ Source
    └─ 관련 Location
```

이 관계는 자동 분석 또는 사용자 수동 등록으로 생성할 수 있다.

---

# 3-B.6 자동 발견과 수동 연결

Asset Registry는 두 방식을 모두 지원해야 한다.

## 자동 발견

Workshop이 게임 소스를 조사하여 후보를 제시한다.

예:

```text
Gloria 조사

자동 발견 후보

✓ 대사 이름: Gloria
✓ Location: estate_office
? 이미지: realtor.png
? 텍스트: 부동산 관리인
```

확실한 것은 자동 연결할 수 있다.

불확실한 것은 사용자에게 후보로 보여준다.

---

## 수동 연결

사용자는 Workshop에서 직접 자산을 선택하여 Entity에 등록할 수 있다.

예:

```text
현재 이미지

content/pic/.../realtor.png

[인물 자산으로 등록]
```

선택:

```text
어느 인물과 연결합니까?

[ Gloria ▼ ]

자산 유형:
[ 고유 이미지 ▼ ]

[등록]
```

이후 `realtor.png`는 Gloria의 등록 자산으로 영구 보존된다.

---

# 3-B.7 현재 장면에서 바로 등록

게임을 플레이하다가:

```text
"이 화면의 realtor.png가 Gloria다."
```

라는 사실을 사용자가 확인했다면 별도의 파일 검색 작업이 필요 없어야 한다.

현재 Image Workshop과 연계하여:

```text
현재 화면 이미지

realtor.png

[이미지 편집]
[자산 등록]
```

을 제공한다.

`자산 등록`:

```text
연결할 인물

Gloria

자산 역할

○ 고유 인물 이미지
○ 이벤트 CG
○ Portrait
○ 배경 속 등장
○ 공용 이미지
○ 기타

[등록]
```

# 3-B.8 기존 자산과 제작 중 자산

Asset Registry는 **현재 게임에서 사용되고 있는 자산만 관리해서는 안 된다.**

사용자가 앞으로 적용하기 위해 제작하고 있는 자산도 동일한 Entity에 등록할 수 있어야 한다.

예:

```text
Gloria

게임 사용 자산
────────────────
realtor.png
estate_scene_1.png


제작 중 자산
────────────────
gloria_new_portrait.png
gloria_room_new.png
gloria_event02_new.png
```

이 기능이 향후 별도 Character/NPC Modding Tool과 연결되는 핵심이다.

---

# 3-B.9 Mod Asset 폴더

게임 원본 리소스와 분리하여 제작 중인 자산을 보관할 전용 영역을 둔다.

개념 구조:

```text
SNKmod/
 └─ Assets/
     ├─ Characters/
     ├─ NPC/
     ├─ Mobs/
     ├─ Slaves/
     ├─ Extras/
     └─ Unassigned/
```

개별 Entity별 하위 폴더 사용도 가능하다.

예:

```text
SNKmod/
 └─ Assets/
     └─ NPC/
         └─ Gloria/
             ├─ portrait/
             ├─ event/
             ├─ working/
             └─ other/
```

정확한 실제 폴더 규칙은 이후 구현 설계에서 확정하되 다음 조건은 지켜야 한다.

> 원본 게임 리소스와 제작 중 모딩 자산을 섞지 않는다.

---

# 3-B.10 제작 중 자산 등록

사용자는 외부에서 제작한 파일을 Asset Registry에 등록할 수 있다.

예:

```text
Gloria
[새 자산 등록]

파일:
G:\...\new_gloria_event.png
```

Workshop은 파일을 지정된 Mod Asset 영역에 등록한다.

등록 정보:

```text
Entity: Gloria

상태:
제작 중

유형:
Event CG

게임 적용:
아직 없음
```

따라서 해당 파일이 아직 어떤 QSP 코드에도 연결되어 있지 않아도 Gloria 검색 결과에 나타난다.

# 3-B.11 자산 상태

모든 Asset Link에는 상태를 둘 수 있다.

기본 상태:

```text
게임 사용 중
제작 중
교체 후보
미사용
보관
```

예:

```text
Gloria

[게임 사용 중]
realtor.png

[제작 중]
gloria_new.png

[교체 후보]
realtor_redesign.png
```

이 상태는 파일 자체를 변경하지 않고 Registry에서 관리한다.

# 3-B.12 연결 근거

자산이 왜 특정 Entity와 연결되어 있는지 기록한다.

예:

```text
realtor.png

Entity:
Gloria

연결 근거:
사용자 직접 등록

등록일:
2026-xx-xx
```

다른 사례:

```text
gloria_event.qsrc

연결 근거:
이름 직접 참조
```

또는:

```text
estate_scene_03.png

연결 근거:
Gloria 이벤트 Location에서 직접 사용
```

연결 근거 유형 예:

```text
파일명 자동 일치
텍스트 이름 일치
Alias 일치
Location 연결
이벤트 실행 관계
사용자 직접 등록
Preset/Patch가 생성
```

# 3-B.13 자동 추론과 확정 연결의 구분

자동 분석으로 발견한 자산과 사용자가 확정한 자산을 구분한다.

예:

```text
Gloria

[등록된 자산]
✓ realtor.png

[자동 발견 후보]
? estate_bg02.png
? realtor_scene3.png
```

`?` 후보는 사용자가:

```text
[Gloria 자산으로 등록]
[관련 없음]
```

중 선택할 수 있다.

한 번 `관련 없음`으로 지정한 후보를 매번 다시 제시하지 않도록 제외 정보도 기록한다.

# 3-B.16 검색 대상

Entity 이름으로 검색했을 때 Registry는 다음을 통합하여 표시한다.

```text
1. Registry에 직접 등록된 자산
2. 제작 중 등록 자산
3. Alias
4. 게임 원본 자동 검색 결과
5. Source Resolver 분석 결과
6. 기존 Patch가 해당 Entity와 연결한 자산
```

중요한 우선순위:

```text
사용자가 확정한 연결
        >
자동 추론 결과
```

이다.

# 3-B.17 Text Workshop과의 차이

Asset Registry의 텍스트 검색은 **텍스트를 수정하기 위한 기능이 아니다.**

예:

```text
Gloria 검색
```

으로:

```text
"Gloria..."
"부동산 관리인이..."
```

를 발견하는 것은 **인물과 텍스트 사이의 관계를 조사하기 위해서**이다.

실제 문장 수정이 필요하면:

```text
[Text Workshop에서 열기]
```

로 넘긴다.

따라서:

```text
Asset Registry
= 무엇이 연결되어 있는지 관리

Text Workshop
= 해당 텍스트 내용을 편집
```

으로 책임을 분리한다.

---

# 3-B.18 Image Workshop과의 차이

동일하다.

Asset Registry:

```text
Gloria → realtor.png
```

라는 관계를 기록한다.

Image Workshop:

```text
realtor.png
```

를 실제로 교체하거나 다른 이미지 참조로 변경한다.

따라서 Registry 상세 화면에서는:

```text
realtor.png

[미리보기]
[Image Workshop에서 열기]
```

를 제공한다.

---

# 3-B.19 Patch와의 연결

Patch로 새로운 자산이 만들어지거나 연결되면 Registry에 기록할 수 있다.

예:

```text
Patch:
Gloria Estate Scene Expansion
```

으로:

```text
gloria_new_event.png
```

이 추가됐다면:

```text
Entity:
Gloria

Asset:
gloria_new_event.png

Origin:
Patch - Gloria Estate Scene Expansion
```

으로 등록한다.

패치를 롤백한다고 해서 제작 원본 자산까지 반드시 삭제해서는 안 된다.

게임 적용 상태와 자산 보유 상태는 별도로 관리한다.

---

# 3-B.20 향후 Modding Tool과의 연결

Asset Registry는 향후 만드는 전문 모딩툴의 공통 자산 DB로 사용한다.

예:

```text
[Gloria]
      ↓
Asset Registry
      ↓
────────────────────────
NPC Modding Tool
Character Modding Tool
Image Workshop
Text Workshop
Patch Builder
────────────────────────
```

따라서 향후 별도 모딩툴에서 `Gloria`를 호출하면 처음부터 파일을 다시 찾는 것이 아니라 기존 Registry를 읽을 수 있어야 한다.

---

# 3-B.21 별도 모딩툴에서 기대되는 사용 예

향후 NPC Modding Tool에서:

```text
대상 인물

[ Gloria ]
```

를 선택하면:

```text
기존 게임 자산:
5

제작 중 자산:
8

관련 이벤트:
3

관련 텍스트:
17

[불러오기]
```

가 가능해야 한다.

이것이 이번 개발에서 Asset Registry를 만드는 가장 중요한 장기적 이유다.

---

# 3-B.22 신규 Entity 등록

게임에 존재하지 않는 새로운 인물도 미리 등록할 수 있어야 한다.

예:

```text
[새 인물 등록]

이름:
Madison

분류:
고유 NPC

[생성]
```

아직 게임 코드에 Madison이 없어도:

```text
SNKmod/Assets/NPC/Madison/
```

에 제작 자산을 넣고 등록할 수 있다.

이후 별도 모딩툴에서 이 Entity를 불러와 실제 이벤트 제작에 사용할 수 있다.

---

# 3-B.23 Entity 이름과 실제 게임 코드 분리

Registry의 Entity 이름은 게임 코드의 실제 변수명 또는 파일명과 동일할 필요가 없다.

예:

```text
Entity:
Gloria

Game resource:
realtor.png

Role:
부동산 관리인
```

이 세 가지는 서로 다른 정보다.

따라서 사용자가 Entity 이름을 `Gloria → Madison`으로 변경한다고 해서 Registry가 자동으로 `realtor.png` 파일명까지 변경해서는 안 된다.

그런 실제 소스/파일 변경은 별도의 편집 작업이어야 한다.

---

# 3-B.24 데이터 지속성

사용자가 수동으로 등록한 연결은 Workshop을 종료해도 유지되어야 한다.

따라서 Registry는 별도 데이터 파일로 저장한다.

개념 예:

```text
SNKmod/
 └─ Workshop/
     └─ registry/
         ├─ entities.json
         ├─ assets.json
         └─ links.json
```

구현 과정에서 하나의 JSON으로 합쳐도 무방하다.

중요한 것은 **게임 원본 소스에서 매번 새로 추론하는 임시 데이터가 아니라 사용자 작업을 축적하는 영구 데이터**라는 점이다.

---

# 3-B.25 백업

Registry 역시 중요한 모딩 데이터이므로 백업 대상이다.

다음 작업 전에 Registry 상태를 기록한다.

```text
Entity 삭제
Entity 병합
대량 Asset Link 변경
Alias 대량 변경
```

개별 자산 하나를 등록할 때마다 전체 게임 백업을 생성할 필요는 없지만 Registry 자체의 변경 기록은 남겨야 한다.

---

# 3-B.26 중복 Entity 처리

예:

```text
Gloria
글로리아
Realtor
```

가 각각 별개의 Entity로 잘못 등록될 수 있다.

이를 해결하기 위해:

```text
[Entity 병합]
```

기능을 제공할 수 있다.

예:

```text
Gloria
+
글로리아

        ↓

Gloria

Alias:
글로리아
```

이 과정에서는 모든 기존 Asset Link를 유지한다.

---

# 3-B.27 핵심 원칙

Asset Registry는 다음 원칙을 따른다.

> **파일 이름이 인물 이름과 같다고 가정하지 않는다.**

> **게임 코드에서 자동으로 찾은 관계와 사용자가 직접 확인한 관계를 함께 관리한다.**

> **아직 게임에 적용되지 않은 제작 중 자산도 동일한 인물에 연결할 수 있다.**

> **Entity 이름, 역할명, 게임 내부 이름, 파일명은 서로 다른 정보로 취급한다.**

> **사용자가 한번 구축한 인물-자산 관계는 다음 모딩 작업에서도 재사용한다.**

따라서 Gloria의 경우 최종적으로:

```text
Gloria
│
├─ Alias
│   ├─ Gloria
│   ├─ 글로리아
│   ├─ realtor
│   └─ 부동산 관리인
│
├─ 기존 게임 자산
│   ├─ realtor.png
│   ├─ 관련 Event CG
│   ├─ 관련 Location
│   └─ 관련 Text
│
└─ 제작 중 자산
    ├─ 신규 Portrait
    ├─ 신규 Event CG
    └─ 기타 Mod Asset
```

와 같은 관계가 누적되어야 한다.

**향후 어떤 JO9 모딩툴에서든 `Gloria` 하나만 호출하면 이 정보 전체를 다시 사용할 수 있는 것이 Asset Registry의 최종 목표다.**
:::

이 기능이 들어가면서 구조가 훨씬 명확해졌습니다. **Resolver는 현재 게임 소스를 분석해서 후보를 찾아내고, Asset Registry는 사람이 확인한 관계와 제작 중 자산을 장기적으로 축적**합니다. 둘을 섞지 않는 것이 중요합니다.

# 4. 개발 단계 및 Text Workshop v0.1 범위

## 4.1 개발 순서

JO9 Workshop은 처음부터 모든 기능을 한 번에 구현하지 않는다.

각 단계의 핵심 기능을 실제 게임에서 충분히 테스트한 뒤 다음 단계로 확장한다.

개발 순서는 다음과 같이 고정한다.

```text
Phase 1
Text Workshop v0.1
대사 / 지문 편집

        ↓ 테스트 및 안정화

Phase 2
Text Workshop 기능 확장
변수 포함 텍스트 / 참조 / Preset

        ↓

Phase 3
Image Workshop 소스 참조 확장
새 이미지 연결 / 이미지 참조 변경 Preset

        ↓

Phase 4
Asset Registry
인물 / 모딩 자산 관리

        ↓

Phase 5
향후 전문 Modding Tool
Character / Slave / NPC 제작 도구
```

Asset Registry는 이번 Text Workshop v0.1 개발에 포함하지 않는다.

별도의 차기 개발 스펙으로 관리한다.

---

# 4.2 Text Workshop v0.1 개발 목표

v0.1의 목표는 하나다.

> **게임 화면에 출력된 순수 대사와 지문을 찾아 안전하게 수정할 수 있게 한다.**

처음부터 QSP의 모든 텍스트 표현을 지원하지 않는다.

v0.1에서는 구조가 명확하고 위험성이 낮은 텍스트만 대상으로 한다.

---

# 4.3 v0.1 편집 대상

v0.1에서 지원하는 기본 대상은 다음과 같다.

### NPC 대사

예:

```text
Gloria:
"Welcome. What can I do for you?"
```

### 주인공 대사

예:

```text
"I came to ask about the property."
```

### 지문 / 서술

예:

```text
The realtor looks through several documents.
```

### 일반적인 장면 설명

예:

```text
You enter the office and find the realtor waiting inside.
```

조건은 다음과 같다.

> 화면에 표시되는 문장과 원본 QSRC의 문자열을 비교적 명확하게 연결할 수 있어야 한다.

---

# 4.4 v0.1에서 지원하지 않는 텍스트

다음 항목은 v0.1에서 편집 대상으로 제공하지 않는다.

## 변수 포함 텍스트

예:

```qsp
'<<$npc_name>> gives you <<reward>> gold.'
```

화면에는:

```text
Gloria gives you 100 gold.
```

로 나타나더라도 v0.1에서는 편집 대상에서 제외한다.

후속 버전에서 토큰 보호 기능과 함께 지원한다.

---

## 문자열 조립

예:

```qsp
$text = $prefix + $npc_name + $suffix
```

완성 문장이 여러 변수 또는 문자열 조각을 조합해 만들어지는 경우도 제외한다.

---

## 변수 자체의 값

예:

```qsp
$npc_name = 'Gloria'
reward = 100
```

v0.1은 변수 편집기가 아니다.

---

## 조건문 및 게임 로직

예:

```qsp
if relation > 50:
```

편집 대상에서 제외한다.

---

## Location / 함수 / 실행 코드

예:

```qsp
gs 'interaction_result'
goto 'estate'
dynamic $code
```

v0.1에서는 표시 및 수정 기능을 제공하지 않는다.

---

## 텍스트 Key 구조 변경

예:

```qsp
$txt['generic_greeting']
```

의 Key를:

```qsp
$txt['gloria_greeting']
```

으로 분리하거나 새 Key를 만드는 기능은 v0.1에 포함하지 않는다.

---

# 4.5 v0.1의 안전 기준

v0.1은 가능한 한 **코드를 수정하는 느낌이 들지 않는 편집기**여야 한다.

사용자가 보는 기본 화면:

```text
현재 장면 텍스트

────────────────────────

Gloria

Welcome. What can I do for you?

[수정]

────────────────────────

You look over the documents on her desk.

[수정]
```

사용자는 실제 문장만 수정한다.

QSP 구문 자체는 기본 UI에 노출하지 않는다.

---

# 4.6 현재 장면 중심

v0.1의 기본 진입점은 전체 텍스트 검색이 아니다.

Image Workshop과 동일하게:

```text
게임 플레이
   ↓
수정할 장면 발견
   ↓
엔진 메뉴
   ↓
[현재 화면 텍스트 편집]
```

으로 진입한다.

Workshop은 현재 장면에서 사용되는 텍스트를 먼저 찾는다.

---

# 4.7 텍스트 사용처 목록

현재 문장이 여러 소스 위치에서 발견되면 자동 전체 치환하지 않는다.

Image Workshop의 이미지 사용처 목록과 동일한 방식으로 후보를 보여준다.

예:

```text
검색 문장:

"Welcome."

발견된 사용처 5개

[현재 장면]
☑ interaction_city
   "Welcome."

[다른 사용처]
☐ estate_intro
   "Welcome."

☐ shop_general
   "Welcome."

☐ guild
   "Welcome."
```

사용자가 선택한 항목만 수정한다.

---

# 4.8 이름 검색 역시 선택식

예를 들어:

```text
Gloria → Madison
```

으로 수정하려고 할 때 `Gloria`라는 문자열을 전체 게임에서 자동 치환하지 않는다.

사용처를 보여준다.

예:

```text
"Gloria" 사용처

[현재 장면]
☐ Gloria: "Welcome."
☐ "You approach Gloria."

[관련 이벤트]
☐ "Return to Gloria tomorrow."

[기타]
☐ "Someone mentions Gloria."
```

사용자가 직접 수정 범위를 선택한다.

v0.1에서는 **일반 출력 텍스트 안에 포함된 이름만** 대상으로 한다.

변수명, Key, Location 이름 등은 포함하지 않는다.

---

# 4.9 v0.1 Source Resolver 범위

Resolver 역시 v0.1에서는 단순하고 신뢰도 높은 경로부터 개발한다.

우선 지원:

```text
1. 현재 Location
2. 화면 문자열 완전 일치
3. 관련 QSRC 내 직접 문자열
4. 텍스트 DB의 직접 문자열
5. 전체 QSRC 문자열 검색
```

후속 버전으로 미룰 것:

```text
변수 흐름 추적
동적 문자열 조립
실행 경로 정밀 추적
조건 분기 해석
복잡한 배열 추적
```

---

# 4.10 문자열 일치 방식

v0.1은 가능한 한 **완전 일치**를 우선한다.

예:

화면:

```text
The realtor smiles.
```

원본:

```qsp
'The realtor smiles.'
```

이면 높은 신뢰도이다.

부분 일치만 가능한 경우에는 자동 수정하지 않고 후보로만 표시한다.

---

# 4.11 수정 전 확인

사용자가 문장을 수정하면 적용 전에 다음 정보를 보여준다.

```text
수정 대상

Location:
interaction_city

원문:
The realtor smiles.

수정문:
Gloria smiles.

사용 위치:
현재 장면 1개

[취소]
[적용]
```

공용 문장이라면 경고한다.

```text
이 문장은 다른 장면에서도 사용되고 있습니다.

선택한 소스 1개만 수정합니다.
```

---

# 4.12 백업

Text Workshop v0.1부터 백업 기능은 필수이다.

기능을 나중 버전으로 미루지 않는다.

모든 수정은 다음 순서를 따른다.

```text
원본 확인
 ↓
SHA-256 기록
 ↓
백업
 ↓
텍스트 수정
 ↓
저장 확인
 ↓
결과 기록
```

적용 도중 실패하면 자동 복원을 시도한다.

---

# 4.13 변경 기록

v0.1부터 최소한의 History 기능을 제공한다.

예:

```text
09:42
interaction_city

The realtor smiles.
↓
Gloria smiles.

[되돌리기]
```

여러 문장을 동시에 수정했다면 하나의 작업 단위로 묶는다.

```text
09:45

Gloria office scene
3개 문장 수정

[상세]
[전체 되돌리기]
```

---

# 4.14 롤백

롤백 시 현재 파일이 수정 당시 예상 상태와 같은지 다시 확인한다.

다른 수정이 이후 적용된 경우 이를 무시하고 원본을 덮어쓰지 않는다.

예:

```text
이 소스는 해당 작업 이후 다시 수정되었습니다.

자동 롤백을 중단했습니다.

[차이 보기]
[취소]
```

강제 복구는 v0.1에서 반드시 제공할 필요는 없다.

안전한 롤백을 우선한다.

---

# 4.15 v0.1에서 Preset은 구현하지 않는다

Preset 개념은 전체 Workshop 설계에는 포함하지만 Text Workshop v0.1에서는 필수 구현 범위가 아니다.

v0.1의 목표는:

```text
발견
→ 선택
→ 문장 수정
→ 백업
→ 적용
→ 롤백
```

의 기본 편집 사이클 검증이다.

Preset은 이 사이클이 안정화된 이후 추가한다.

---

# 4.16 v0.1 테스트 목표

개발 완료 여부를 기능 수로 판단하지 않는다.

실제 JO9 플레이에서 다음 테스트를 수행해야 한다.

### 테스트 A — 단일 대사

```text
대사 1개 발견
→ 수정
→ 게임 반영 확인
→ 롤백
→ 원문 복구 확인
```

### 테스트 B — 지문

```text
지문 발견
→ 수정
→ 게임 반영
```

### 테스트 C — 같은 문장의 여러 사용처

```text
동일 문자열 여러 위치 발견
→ 목록 표시
→ 한 곳만 선택
→ 선택 위치만 변경
```

### 테스트 D — 이름 포함 문장

```text
Gloria 문자열 검색
→ 사용처 목록
→ 일부만 Madison으로 변경
→ 나머지 Gloria 유지
```

### 테스트 E — 잘못된 후보

Resolver가 여러 후보를 반환하는 경우:

```text
사용자 선택 전 수정 없음
```

을 확인한다.

### 테스트 F — 실패 롤백

의도적으로 저장 또는 검증 실패를 발생시키고:

```text
자동 복구
```

가 정상적으로 이루어지는지 확인한다.

# 5. Text Workshop v0.1 화면 및 UX 설계

## 5.1 UX 목표

Text Workshop v0.1의 핵심 목표는 다음 한 문장으로 정의한다.

> 게임에서 보고 있는 대사와 지문을, 이미지 편집기와 비슷한 방식으로 찾아서 선택하고 수정한다.

사용자는 QSP 소스를 직접 찾아갈 필요가 없어야 한다.

기본 흐름은 다음과 같다.

```text
게임 플레이
   ↓
수정하고 싶은 대사/지문 발견
   ↓
엔진 메뉴
   ↓
[현재 화면 텍스트 편집]
   ↓
현재 장면 텍스트 목록
   ↓
수정할 항목 선택
   ↓
원문 / 수정문 확인
   ↓
백업
   ↓
적용
   ↓
결과 확인
```

---

# 5.2 엔진 메뉴 진입

기존 이미지 편집기와 동일한 위치에서 진입한다.

예:

```text
JO9 Workshop

[현재 화면 이미지 편집]
[현재 화면 텍스트 편집]
```

v0.1에서는 Text Workshop을 별도 HTML 페이지로 열어도 되고, 기존 Workshop HTML 내부의 별도 모드로 분기해도 된다.

중요한 것은 사용자가 게임 외부에서 파일을 먼저 찾을 필요가 없어야 한다는 점이다.

---

# 5.3 Workshop 최초 화면

Text Workshop을 열면 가장 먼저 현재 게임 Context를 읽는다.

정상 연결 시:

```text
JO9 TEXT WORKSHOP
현재 화면 텍스트 편집

게임 연결됨
Location: interaction_city

현재 화면에서 텍스트를 찾는 중...
```

탐색 완료 후:

```text
JO9 TEXT WORKSHOP

현재 Location
interaction_city

발견된 텍스트
5개
```

---

# 5.4 현재 화면 텍스트 목록

기본 화면에는 현재 화면과 관련성이 높은 텍스트를 카드 또는 리스트 형태로 표시한다.

예:

```text
────────────────────────────

Gloria

"Welcome. What can I do for you?"

종류: 대사
현재 장면 직접 사용

[수정]

────────────────────────────

"The realtor looks through several documents."

종류: 지문
현재 장면 직접 사용

[수정]

────────────────────────────
```

사용자는 QSRC 파일명이나 코드부터 보지 않는다.

---

# 5.5 텍스트 유형 표시

v0.1에서는 최소한 다음 두 종류를 구분한다.

```text
대사
지문
```

추가로 필요하면 다음을 표시할 수 있다.

```text
선택지
장면 설명
```

단, v0.1에서 편집 가능한 것은 **순수 문자열로 확인된 항목만**이다.

변수가 포함된 경우:

```text
이 항목은 변수 포함 텍스트입니다.
v0.1에서는 편집할 수 없습니다.

[원문 보기]
```

처럼 표시한다.

---

# 5.6 수정 버튼

사용자가 `[수정]`을 누르면 편집 화면으로 이동한다.

예:

```text
텍스트 수정

원문
────────────────────
Welcome. What can I do for you?
────────────────────

수정문
────────────────────
[ Welcome back. What can I do for you? ]
────────────────────

[취소]
[적용 전 확인]
```

기본적으로 원문은 읽기 전용이다.

---

# 5.7 줄바꿈 유지

대사 또는 지문이 여러 줄인 경우 줄바꿈을 유지한다.

예:

```text
원문

Welcome.

What can I do for you?
```

수정창에서도 동일한 줄 구조를 보여준다.

적용 시 사용자가 작성한 줄바꿈을 그대로 보존한다.

---

# 5.8 특수문자 보호

QSP 문자열에서 의미가 있는 따옴표나 기타 구문 때문에 코드가 깨질 수 있다.

v0.1에서는 사용자가 QSP escaping 규칙을 알 필요가 없어야 한다.

예:

사용자가 입력:

```text
"Don't worry," Gloria says.
```

Workshop 내부에서 필요한 escaping을 처리한다.

적용 전 문법 검사를 통과하지 못하면 저장하지 않는다.

---

# 5.9 검색 결과가 하나인 경우

현재 화면 문장이 소스에서 하나만 발견되고 현재 Location과도 일치하면:

```text
원본 위치 확인됨
현재 장면에서 직접 사용
```

으로 표시한다.

이 경우 바로 수정 가능하다.

---

# 5.10 검색 결과가 여러 개인 경우

동일 문장이 여러 곳에서 사용되면 곧바로 편집 화면으로 가지 않는다.

먼저 사용 위치 선택 화면을 보여준다.

예:

```text
"Welcome."

동일 문장 사용처 5개

[현재 장면]
☑ interaction_city
   현재 화면과 직접 연결

[기타]
☐ shop_general
☐ guild
☐ estate_intro
☐ tavern
```

기본 선택은 **현재 장면과 확인된 항목만** 한다.

전체 선택은 자동으로 하지 않는다.

---

# 5.11 현재 장면 우선 정렬

검색 결과는 다음 순서로 정렬한다.

```text
1. 현재 Location에서 직접 출력
2. 현재 Location이 직접 참조
3. 현재 호출 흐름과 관련
4. 기타 동일 문자열
```

사용자는 먼저 현재 장면과 관련된 결과를 봐야 한다.

---

# 5.12 사용 위치 선택 UX

각 사용처에는 최소한 다음 정보를 표시한다.

```text
Location
간단한 주변 문맥
현재 장면 관련 여부
```

예:

```text
☐ estate_intro

... you enter the office.
"Welcome."
The realtor closes the door ...
```

파일 경로나 줄 번호는 기본 화면에서는 숨겨도 된다.

---

# 5.13 주변 문맥 표시

같은 짧은 문장이 여러 곳에 있을 경우 Location 이름만으로 구분하기 어렵다.

따라서 앞뒤 문장을 일부 보여준다.

예:

```text
guild

Before:
The clerk looks up.

Target:
"Welcome."

After:
"What business brings you here?"
```

이를 통해 사용자가 정확한 사용처를 판단할 수 있게 한다.

---

# 5.14 이름 문자열 검색

v0.1에서도 일반 출력 텍스트 안의 이름을 검색하고 선택적으로 수정할 수 있다.

예:

```text
검색
[ Gloria________________ ]

[검색]
```

결과:

```text
Gloria — 14건 발견

[현재 장면 관련]
☐ "Gloria smiles."
☐ "You speak to Gloria."

[다른 장면]
☐ "Return to Gloria tomorrow."
☐ "Ask Gloria about the estate."
...
```

사용자가 원하는 문장만 선택한다.

---

# 5.15 전역 치환 금지

v0.1에서는 다음과 같은 기능을 기본 제공하지 않는다.

```text
Gloria → Madison
[전 게임 일괄 치환]
```

대신:

```text
Gloria 사용처 검색
      ↓
목록
      ↓
사용자가 선택
      ↓
선택한 문장만 변경
```

방식을 사용한다.

---

# 5.16 일괄 선택 보조

사용자가 결과를 빠르게 선택할 수 있도록 다음 정도의 보조 기능은 허용한다.

```text
[현재 장면만 선택]
[현재 Location 선택]
[선택 해제]
```

`전체 선택`을 제공할 경우 눈에 띄는 경고를 표시한다.

v0.1에서는 전체 선택 버튼 자체를 생략해도 된다.

---

# 5.17 수정 전 확인 화면

적용 직전에 변경 내용을 보여준다.

예:

```text
변경 확인

대상:
interaction_city

원문:
Welcome.

수정:
Welcome back.

변경 항목:
1개

[취소]
[적용]
```

여러 건 수정 시:

```text
변경 항목 4개

[변경 내용 펼쳐보기]
```

를 제공한다.

---

# 5.18 적용 시 백업

사용자가 `[적용]`을 누르면 UI에서 바로 파일을 덮어쓰지 않는다.

처리 순서:

```text
1. 현재 원본 재확인
2. 최초 탐색 당시 해시와 비교
3. 백업 생성
4. 수정 적용
5. 수정본 재읽기
6. 저장 결과 확인
7. History 기록
```

---

# 5.19 원본이 중간에 변경된 경우

사용자가 Workshop을 열어둔 사이 다른 패치가 적용될 수 있다.

따라서 탐색 당시 원본과 적용 직전 원본이 다르면 중단한다.

예:

```text
원본 소스가 Workshop을 연 이후 변경되었습니다.

안전을 위해 적용을 중단했습니다.

[다시 검색]
[취소]
```

자동 덮어쓰기는 하지 않는다.

---

# 5.20 적용 성공 화면

정상 적용 시:

```text
수정 완료

1개 텍스트가 변경되었습니다.

백업:
정상 생성

[게임으로 돌아가기]
[변경 기록 보기]
```

게임에 즉시 반영되지 않고 화면 갱신이나 재실행이 필요하다면 명확히 표시한다.

예:

```text
게임 화면을 다시 열면 변경 내용을 확인할 수 있습니다.
```

---

# 5.21 적용 실패 화면

적용 중 오류 발생 시:

```text
수정 실패

변경 작업을 완료하지 못했습니다.

원본 상태로 자동 복구:
성공

게임 파일은 수정 전 상태입니다.

[오류 내용]
[닫기]
```

자동 복구까지 실패한 경우에는 별도 고위험 경고를 표시한다.

---

# 5.22 변경 기록 화면

상단 또는 별도 메뉴:

```text
[변경 기록 / 복구]
```

화면:

```text
09:30
interaction_city

"Welcome."
→
"Welcome back."

[상세]
[되돌리기]
```

---

# 5.23 여러 항목을 동시에 수정한 작업

한 번의 적용에서 여러 문장을 수정했다면 하나의 작업으로 묶는다.

예:

```text
09:38

Gloria office scene
텍스트 4개 수정

[상세]
[전체 되돌리기]
```

상세:

```text
1.
Welcome.
→
Welcome back.

2.
The realtor smiles.
→
Gloria smiles.

3.
...
```

---

# 5.24 개별 롤백과 작업 롤백

가능하다면 두 방식을 지원한다.

```text
개별 항목 되돌리기
전체 작업 되돌리기
```

단 v0.1 구현 복잡도가 커질 경우 **작업 단위 롤백을 우선**한다.

안전성이 더 중요하다.

---

# 5.25 롤백 충돌

롤백 대상 파일이 이후 다른 작업으로 수정되었다면 즉시 덮어쓰지 않는다.

예:

```text
이 파일에는 이후 다른 변경이 있습니다.

자동 복구를 중단했습니다.

[현재 내용 확인]
[취소]
```

v0.1에서는 강제 덮어쓰기를 제공하지 않아도 된다.

---

# 5.26 편집 불가 항목

Resolver가 발견했지만 v0.1 지원 범위를 벗어난 경우 목록에서 숨기기보다 표시하되 비활성화한다.

예:

```text
Gloria gives you 100 gold.

[변수 포함 텍스트]

현재 버전에서는 직접 수정할 수 없습니다.

[원문 보기]
```

이렇게 해야 사용자가 "왜 화면의 문장이 검색되지 않는가"를 이해할 수 있다.

---

# 5.27 검색되지 않은 화면 텍스트

자동 탐색에서 원하는 문장이 나오지 않을 경우:

```text
[현재 화면에 없는 텍스트 검색]
```

을 제공한다.

사용자가 실제 화면의 문장을 입력한다.

예:


# 5.37 UX 핵심 규칙

Text Workshop v0.1은 다음 규칙을 반드시 지킨다.

> 현재 화면을 기준으로 시작한다.

> 자동 전역 치환하지 않는다.

> 동일 문자열의 모든 사용처를 보여주고 사용자가 선택하게 한다.

> 현재 장면과 직접 연결된 결과를 가장 먼저 보여준다.

> 변수와 실행 코드는 v0.1에서 일반 텍스트처럼 수정하지 않는다.

> 적용하기 전에 변경 전후를 보여준다.

> 모든 실제 수정은 백업 이후 수행한다.

> 실패 시 가능한 한 자동 롤백한다.

> 기존 Image Workshop과 다른 프로그램을 쓰는 느낌이 들지 않도록 한다.
